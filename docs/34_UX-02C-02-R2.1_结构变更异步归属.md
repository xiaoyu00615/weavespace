# UX-02C-02-R2.1：结构变更的异步归属、目标身份与交互收尾

> 基线：`de11804`（R2，已通过复审）。本轮只关闭已确认的缺陷，不重写已冻结的方案。
> 主体方案（500ms 双击仲裁、身份三态与对称降级、首屏/续页身份能力、项目改名
> 全局/会话分层、sourceAnchor 强制契约、Host 屏障内独立核验、Provider 两阶段核验、
> 源对象变化后刷新源父层、元数据逐条核验迁移）**全部保持不变**。

---

## 一、R2 之后还差什么

R2 把"要改的是**哪个源对象**"钉死了：意图冻结源锚、Host 屏障内重算、Provider
动手前再核一次。但一次改名/移动是"多段 `await` + 多个副作用"的组合，还有两件事
没有被钉住：

1. **这条结果该不该写进这一屏。** 请求在旧世界里发出、结果在新世界里回来——
   旧工作区的 `APPLIED` 会作废新工作区的层表，旧请求的 `UNKNOWN` 会在新工作区
   触发只读刷新，旧请求的拒绝原因会写进另一个会话的输入框。
2. **搬进哪个目录。** 源身份有了，**目标目录**没有：用户在对话框里选中的文件夹，
   到 Host 动手时可能已经被外部删掉重建。

外加两处交互与表述的收尾：提交期间输入框 `disabled` 导致焦点被扔到 `body`，
结果回来后没人还焦点（Escape / Enter 按在 `body` 上）；`docs/33` §五 关于
"元数据不迁移"的表述与实际实现相反。

三层因果可以并列成一句话：**源对象是谁 → 结果写给谁 → 搬进哪个目录**。
三层用的是同一个模式：**显式参数 + 每一层独立重算/核验**，谁也不采信上一层的自述。

## 二、世界票据（B01）

```ts
interface StructureWorld {
  mode: string;          // live / demo
  workspaceMode: string; // multi / legacy / static
  workspaceKey: string | null;
  epoch: number;         // createLoadEpoch 的代次
}
```

- **四维缺一不可**：`Live → Demo → Live` 之后 `mode` 又变回 `live`，只有 `epoch`
  能证明"这一轮已经不是刚才那一轮"。
- **刻意不含 `activeProjectId`**：同一工作区内切换活动项目，不该阻止原项目
  真实结构变化的同步——那是两件不同的事（B03 明确要求）。这条差异在
  `structure-ownership.ts` 与 `structure-intent.ts` 两处都写了注释。
- **冻结而非自动更新**：意图打开时冻结一份；提交时逐项核验。把预期悄悄换成
  最新值，等于把"改的已经不是那个对象/那个世界了"藏起来。

### 闸门纪律

```ts
const guard = createStaleGuard(intent.world, () => host.world());
if (guard.check()) return; // 每次 await 之后、每次 dispatch 之前
```

- 只判一次不够——那正是 R2.1 要消灭的缺口；
- 作废**不可撤销**（代次只增不减），作废之后**一个副作用都不发**：不
  `invalidateLevel`、不 `load`、不 `expandFolder`、不 `dispatch`；
- 唯一的对外表达是一条全局提示：**"Host 已改完 / 这一屏没回填 / 不会自动重发"**。

## 三、提交前的三段核验（B01）

顺序固定，因为对用户是三件事：

| 顺序 | 判据 | 文案方向 |
|---|---|---|
| 1 | 会话票据还属于当前输入行 | "这次操作所属的输入已经结束" |
| 2 | 世界四维 | "工作区已经切换 / 已重新加载，结果没有写入当前界面" |
| 3 | 源锚与身份状态 | "这一行对应的对象已经变化" |

`verifyIntent({ intent })` 接收的是**本次提交实际使用的那一份冻结意图**，
不是按 `projectId + sourcePath` 现查"最新意图"——同一行先后开过两个会话时，
后者会把前者顶掉，核验的对象就不是要提交的那个了（B04）。

## 四、结果落地：三条路径，同一套归属（B03）

| Host 结果 | 界面动作 | 跨世界时 |
|---|---|---|
| `APPLIED` | 作废旧路径下已加载的层 → 源父层/目标父层各自作废 → `TREE_STRUCTURE_CHANGED` → 重取两层 → 展开目标祖先 | 零副作用 + 一条"已改完但没回填"提示 |
| `UNKNOWN` | 恰好一次只读核对（刷源父层与目标父层），**不重发、不改草稿** | 一次请求都不发 |
| `REJECTED` | 错误写进**发起这次请求的那个**行内界面；只有"源真的变了"（`ERR_ENTRY_SOURCE_CHANGED` / `ERR_RESOURCE_NOT_FOUND`）才重取源父层 | 不重取 |

**实际结果与界面回填分离**：Host 说 `APPLIED` 就是 `APPLIED`，界面没写进去
不等于失败。反过来，界面回填成功也不能把 `UNKNOWN` 说成成功。

> **R2.2 补充（2026-11）**：`UNKNOWN` 的"只读核对"本身也有三种结局——真的执行了、
> 因世界切换被闸门挡下（零请求）、执行失败。提示必须按真实结局说话，不能零请求
> 还写"已刷新源位置与目标位置"（`structureUnknownNotice`）。

**行内提示按会话票据路由**（B02）：`inlineNoticeTargets` 只认票据，不认
`projectId + path`；旧会话的迟到结果两个行内界面都不写，只落状态栏。

## 五、移动目标目录身份（D）

- 目标身份复用**资源锚**：普通文件夹用 `metadataAnchorOf({projectId, path, rootToken, identity})`，
  项目根用 `projectAnchor`（根没有 `dev:ino`，它的身份是根令牌摘要）。
- 对话框在**选择目标时**捕获身份，重新选择捕获新的；提交时随请求发出 `targetAnchor`。
- 形状非法 / 缺失 → Shell 本地拒绝（`MISSING_TARGET_INTENT_NOTICE`），零请求。
- Host 在屏障内自己读一次目标身份、自己重算锚再比对：
  - 读不到（目录没了）→ `ERR_ENTRY_PARENT_INVALID`（用户要做的是重选）；
  - 读到了但不是那一个（删除重建）→ `ERR_ENTRY_TARGET_CHANGED`（与"源变了"分开）。
- Provider 在建立目标占位前、`rename` 前各核一次目录连续性（普通目录、非链接/
  非不可信重解析点、`dev:ino` 相符）。
- **不引入根级旁路**：真实改名的目标父目录仍由 Host 派生，客户端不能自由指定
  改名目录。

## 六、Provider 侧的三处收尾（C）

### C01 改名前的源对象完整核验

在接近副作用处再核一次，顺序是**结构 → 类型 → 身份**：

1. 是链接 / 不可信重解析点 → `ERR_ENTRY_SOURCE_INVALID`（沿链接改名会改到根外的对象，
   比"改错文件"更严重）；
2. 类型与第一次判定不一致 → `ERR_ENTRY_SOURCE_INVALID`（`dev:ino` 相同只证明"同一个
   inode"，这里要证明的是"还是那个普通文件/目录本身"）；
3. `dev:ino` 不符 → `ERR_ENTRY_SOURCE_CHANGED`。

### C02 `verify()` 只认对象身份

`rename` 不换 inode，所以"目标身份 == 源身份"是成功率最高的证据。下面四项
**都不是**独立成功依据：源路径消失、目标存在、内容 SHA-256 相同、目录结构指纹相同。
外部在中间删掉刚搬过去的文件、再放一个内容一模一样的新文件，这四项全部成立，
而用户的数据已经丢了。证明不了 → `UNKNOWN`。Windows 大小写仅变化分支同样核身份，
"名称正确"不算成功。

### C03 新增源终检带来的窗口

源终检是一次异步 `lstat`，它确实把"目标占位核验"到 `rename` 之间的窗口拉长了一点。
收紧方式：

- **顺序：先认源、后认目标。** 最后一次目标核验紧贴 `rename`，它保护"绝不覆盖外部对象"；
- 10d 内部再规定**先认目录、后认占位**：目录已经不是用户选中的那个时，绝不
  "顺手重新占位"，否则会在用户从未确认过的目录里留下本次操作的痕迹；
- 占位归属仍只有 `owned` 可覆盖或删除；`foreign` → 拒绝/`UNKNOWN`，绝不删外部对象。

> **R2.2 勘误（2026-11）**：上面这条"目录已经不是用户选中的那个 → 拒绝"只对
> **尚未建立占位**的情形成立。占位一旦建立，它就住在目录里：目录被整体移走/删除重建后，
> 占位随之前往别处（或随旧目录消失），此时**不能**再宣称"零副作用"，
> 只能返回 `UNKNOWN`。详见 `docs/35_UX-02C-02-R2.2_占位收敛与异常恢复.md` §二。
> 本节的顺序与窗口分析仍然有效，只是结果语义按"占位是否已建立"分叉。

> **R2.2-PATCH 勘误（2026-11）**：本节描述的目标目录连续性**当时只在调用方传了
> `expectedTargetIdentity` 时才生效**——普通改名与项目根目标不传这个参数，
> `targetDirStillMatches()` 直接 `return true`。也就是说上面的第三点（先认目录、
> 后认占位）在改名路径上其实没有防线。补丁改为保存"本次执行读到的父目录身份"
> 作为**内部基准**，见 `docs/35` §七。

OS 级 TOCTOU（复核与 `RenameFile` 之间）**仍然存在**，不宣称消除。

### C04 `dev:ino` 的数字精度（本轮只记录，不改实现）

实测（本机 Windows / NTFS，200 个新文件）：

| 指标 | 实测值 |
|---|---|
| `ino > Number.MAX_SAFE_INTEGER` | 10 / 200 |
| `BigInt(number) !== bigint ino`（已丢精度） | 7 / 200 |
| 两个不同 inode 被表示成同一个 number | 0 / 200 |

结论：身份字符串是 `${dev}:${ino}`，两侧都用同一套 number 转换，所以**比较是
自洽的**；真实失败模式只有一种——两个不同对象的 ino 在双精度下舍入到同一个值。
改用 `bigint` 必须先评估元数据、隐藏记录、回收区与历史持久化里已存的
`dev:ino` 字符串（它们都是十进制字符串，混入 bigint 会出现"同对象不同串"），
因此本轮**只作为独立架构风险记录**（见 §十 R21-R1），不夹带在收尾里改。

## 七、项目显示名的两个边界（A）

- **A01** 提交前必须同步核验"打开会话那一刻的活动项目"与"现在的活动项目"：
  会话清理是 `useEffect`、提交是事件回调，两者之间有一个窗口，切换当前项目后的
  第一次 Enter 会落在旧会话上。**不能**直接比较 `session.projectId` 与活动项目——
  右键菜单可以给**非当前项目**改显示名。
- **A02** Host `APPLIED` 且 `backfill=stale` 时，即使行内会话仍存在，也必须明确
  告知三件事：Host 已改名 / 列表未回填 / 未自动重发，然后才关闭会话。静默关闭会
  让用户以为没改成，再改一次会撞上"名称已被其他操作修改"。

## 八、失焦与键盘交互（E）

`apps/shell/src/components/focus-restore.ts` 把"该不该还焦点"抽成纯模块：

```ts
focusWhereOf(active, own): 'self' | 'body' | 'elsewhere'
shouldRestoreFocus({ ended, sessionCurrent, atStart, now }): boolean
```

三条纪律：

1. **只还给自己**（`body` 也算自己）；
2. **只在请求真的结束那一帧还**（`submitting` true→false 的那次渲染）；
3. **只还给同一个会话**（旧请求回来时新会话已经打开/收起就不还）。

配套：`Enter` 按既有契约提交（排除 `TEXTAREA`，`preventDefault` 挡掉按钮原生激活，
提交中忽略）；`Escape` 取消；`REJECTED` / `blocked` 保留输入；`APPLIED` / `UNKNOWN`
不复活已关闭会话；正文编辑器与其他模块的焦点永不被抢。

## 九、不变量

1. 任何一次结构变更都必须带**源锚**与**世界票据**；缺一即本地拒绝，零请求。
2. 移动还必须带**目标锚**；缺失 / 形状非法 → 拒绝，绝不"先搬过去再说"。
3. 每一次 `await` 之后、每一次 `dispatch` 之前都要过闸门；作废后零副作用。
4. 结果只写入**发起它的那个会话**；票据不符只落状态栏。
5. `APPLIED` 必须由 Host 明确给出；`UNKNOWN` 只做一次只读核对，不自动重试。
6. Provider 的成功只认"目标身份 == 源身份"；四项外观证据都不算。
7. 目标目录/目标占位在动手前的最后核验不可省；`foreign` 绝不删除。
8. 焦点只在"结束 + 同一会话 + 没跑到别处"时归还。

## 十、剩余风险与边界

| 编号 | 风险 | 状态 |
|---|---|---|
| R21-R1 | `dev:ino` 双精度舍入：两个不同 inode 可能比较相等 | 已测量（见 §六 C04），本轮不修，需先评估持久化兼容 |
| R21-R2 | 复核与 `RenameFile` 之间的 OS 级 TOCTOU | 未消除，已披露 |
| R21-R3 | 目标目录在 10d 之后、`rename` 之前被替换 | 未消除（窗口已收缩到最小） |
| R21-R4 | 网络文件系统 / 容器挂载上的 `dev`/`ino` 稳定性 | 依赖本地文件系统，不保证 |
| R21-R5 | 真实 Windows 原生目录选择对话框 | 本轮不涉及（沿用既有未验证事实） |
| R21-R6 | 移动目标只在**同项目内**；跨项目移动不提供 | 产品边界，非缺陷 |
