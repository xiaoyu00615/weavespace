## A. 项目定义

### A.1 定义【拟议】

> **项目 = 用户主动添加到左侧列表中的一个文件夹，它就是该项目唯一的授权根目录。**

- 信息来源只有一个：本机原生选择器（ADR-021 T3）确认后由 Host 签发；`ProjectStore` 持久化。
- 一个项目 = 一个目录 + 一个不可变 `projectId` + 一个可改的显示名 + 一条授权记录。
- 项目内部**任意数量、任意层级**的子文件夹与文件都属于同一个项目。
- **子文件夹永不自动成为独立项目**。没有"扫描目录发现项目"、没有"把子目录提升为项目"、没有"批量导入目录"这类入口。

### A.2 名称与路径是两个概念【拟议】

| 概念 | 可变性 | 是否持久化 | 是否对网页可见 |
|---|---|---|---|
| `projectId` | **不可变**（Host 签发，不复用，含已撤销的 id） | 是 | 是（仅标识，不是路径） |
| `name`（显示名） | 可改，任意时刻 | 是 | 是 |
| `rootDir`（真实路径） | 不可改（改路径 = 移除后重新添加） | 是 | **否**（任何响应都不返回） |
| 磁盘上的文件夹名 | **WeaveSpace 永不修改** | — | 间接可见（作为树节点名） |

重命名只改 `name`：`projectId`、`rootToken`、`workspaceKey` 的根身份组成不变（ADR-022 §4.3 已有事务定义，本轮不改）。**不发起任何 `fs.rename`**。

### A.3 项目集合的持久化【拟议】

- 项目集合由 `ProjectStore`（v2：`commitSeq` / `issuedIds` / `revoked[]` / 墓碑日志 / 单实例锁）自动维护，写入只能由 Host 事务产生（ADR-022 §3–§4）。
- **用户不需要、也不应该手工编辑 `workspace.json`**。该文件不是面向用户的配置入口；它是 Host 的持久化状态。
- 启动时由 Host 读取并复核根身份；根不可用的项目以 `UNAVAILABLE` 呈现，而不是从列表中消失（ADR-023）。

### A.4 明确保留的限制【拟议】

| 限制 | 保留理由 |
|---|---|
| 重复根拒绝（`ERR_PROJECT_DUPLICATE_ROOT`） | 两个项目指向同一目录会让"移除 A"与"B 仍可用"产生授权歧义 |
| 嵌套根拒绝（`ERR_PROJECT_NESTED_ROOT`，含 Windows 大小写折叠） | 外层根可枚举内层根，等于绕过"逐项目授权" |
| 不自动发现项目 | 自动发现 = 未经用户确认就扩权，违反 ADR-021 T3 |
| 不 adopt / 不 rebind | 根被替换后重新确认身份必须重新走一次人工授权（A2 再议） |
| UNC / 设备路径 / 重解析点不可作为根 | 沿用 `inspectProjectRoot`（`packages/project-registry/root-status.ts`） |

**本轮不修改任何授权边界**。上述限制一条都不放宽；嵌套根之所以继续拒绝，正是因为"一个项目可以任意深度"，深度需求由树满足，不需要靠嵌套授权。

### A.5 被否决的替代设计

| 方案 | 否决理由 |
|---|---|
| 一个根下每个子目录自动成为项目 | 直接把"树的层级"与"授权单元"混为一谈；用户会看到成百上千个"项目"，且每个都自带一份授权记录 |
| 提供"输入路径添加项目" | 网页拿不到可信绝对路径，等于接受网页伪造路径（ADR-021 F4） |
| 让用户手工维护 `workspace.json` | 把持久化一致性（`commitSeq` / 墓碑 / 哈希链）交给人工，必然产生不可恢复的错位 |

## B. 完整真实文件树

### B.1 展示规则【拟议】

必须展示授权根目录下**所有可枚举**的文件夹与文件：

- 文本、代码、图片、视频、音频、PDF、JSON、二进制、无扩展名文件**一律显示**。
- **文件类型不决定是否显示**，只决定"能否预览/编辑"。
- 空文件夹必须出现（与"读不出来"严格区分，见 B.6）。
- 支持任意层级。
- 不支持预览的文件仍是**普通文件节点**：可选中、可看到名称与扩展名，点击时给出"此类型暂不支持预览"的明确提示，而不是消失或弹原始错误码。

### B.2 按需展开与分页【拟议】

- 一次请求只取**一层**：`GET /api/tree?projectId=<id>&dir=<相对路径>&cursor=<游标>&limit=<条数>`，
  `dir` 省略或空串表示项目根。
- 父目录首次展开时才请求子层；已加载的子层缓存在 Shell，刷新只作废当前项目的缓存。
- **不做**递归全量扫描、不做后台预取、不做文件系统监听（沿用"刷新是显式动作"）。
- **分页（R1 修订）**：`limit` 是**每页**条数，默认 200、上限 2000；它**不是**单层可见上限。
  一页没取完时响应给出 `page.nextCursor`，客户端用同一个 `dir` + 该游标继续请求，
  **直到 `nextCursor === null` 为止**——其结果必须是"该层所有可枚举条目都可见"，
  而不是"只显示前 N 项"。`page.total` 给出该层总条目数，供 UI 显示"已显示 200 / 2001"。
- **稳定排序是分页的前提**：服务端对该层全量排序后再切片，比较器固定为
  「目录/链接在前、文件在后」→ `localeCompare(name, 'zh-Hans-CN')` → 名称码点序兜底，
  因此同一次请求序列内的分页顺序不会漂移（详见 B.4）。
- 游标语义是**同一目录快照内的偏移量**，不是跨快照的游标：目录内容在两页之间变化时，
  后续页可能出现重复或遗漏，UI 必须把"刷新"作为唯一的重置手段（B.2.1）。
- 不提供 `hasChildren` 预判：要判断子目录是否为空必须再 `readdir` 每个子目录，那等于把递归扫描藏在"一层"接口里。空与否在展开时才知道。

#### B.2.1 分页协议【拟议】

| 字段 | 方向 | 说明 |
|---|---|---|
| `dir` | 请求 | 项目内相对路径；省略/空串 = 根 |
| `cursor` | 请求 | 不透明字符串；省略 = 第一页。当前实现为十进制偏移量，客户端**不得**解析或构造 |
| `limit` | 请求 | 每页条数；缺省 200，范围 1–2000，越界 → `400 ERR_COMMAND_INVALID`（零 IO） |
| `entries` | 响应 | 本页条目，已按 B.4 排序 |
| `page.limit` | 响应 | 实际生效的每页条数（回显，便于客户端计算进度） |
| `page.cursor` | 响应 | 本次请求的游标；第一页为 `null` |
| `page.nextCursor` | 响应 | 下一页游标；`null` 表示**该层已全部取完** |
| `page.total` | 响应 | 该层总条目数（不受 `limit` 影响） |

强约束：

1. **禁止静默截断**：只要还有剩余条目，`nextCursor` 就必须非 `null`；
   "返回一页就结束、剩下的丢掉"属于缺陷。
2. `nextCursor === null` 时，本次响应必须已经覆盖该层全部条目。
3. 游标非法（负数、非整数、含字符）→ `400 ERR_COMMAND_INVALID`，**不读盘**。
4. 游标超出总数（目录变小了）→ `200` + `entries: []` + `nextCursor: null`，不报错（幂等终点）。
5. 客户端必须保留**每个目录的已加载页序列**，追加而不是替换；只有"刷新该目录/该项目"
   才清空序列并回到第一页。

### B.3 节点模型【拟议】

```ts
type NodeKind = 'folder' | 'file' | 'link';

interface TreeEntryDto {
  /**
   * 稳定 id，三套**互不重叠**的命名空间（R1 修订）：
   *   目录 `dir:<projectId>/<relPath>`
   *   文件 `doc:<projectId>/<relPath>`
   *   链接 `link:<projectId>/<relPath>`
   * Legacy（无 projectId）退化为 `dir:<relPath>` / `doc:<relPath>` / `link:<relPath>`。
   */
  id: string;
  name: string;          // 单段名称，不含路径分隔符
  kind: NodeKind;
  /** 小写含点；无扩展名或目录为空串/undefined。 */
  extension?: string;
  /** 项目内相对路径，正斜杠分隔。**永不是绝对路径。** */
  relPath: string;
}

interface TreePageDto {
  status: 'APPLIED';
  /** 本层条目，已排序（见 B.4）。 */
  entries: TreeEntryDto[];
  page: {
    limit: number;
    /** 本次请求的游标；第一页为 null。 */
    cursor: string | null;
    /** 下一页游标；null = 该层已全部取完。 */
    nextCursor: string | null;
    /** 该层总条目数。 */
    total: number;
  };
}
```

- `kind` 只有三种，**不携带格式语义**。`markdown` / `text` 这类"格式即类型"的表达必须消失——它把渲染决策塞进了数据契约（违反 `apps/shell/src/state/types.ts` 的注释约定与 ARCH-001）。
- 格式一律由 `extension` + 能力注册表（`apps/shell/src/capabilities/registry.ts` 的 `resolveViewer`）决定。
- **`link` 必须有独立的 `link:` 前缀**（R1 修订）。理由：链接既不是可展开的目录，也不是可打开的文档；
  若它与 `dir:` 或 `doc:` 共用前缀，任何"按前缀分流"的代码都会把它当目录/文件处理，
  进而触发展开或打开这两个被 B.5 明确禁止的动作。同一 `relPath` 在三种命名空间下
  得到三个不同 id，这也让"链接不会与同名真实条目撞 id"成为结构性事实而不是约定。

### B.4 排序【拟议】

沿用并收紧现有 `sortNodes` 语义（`apps/server/src/tree.ts:35-41`），形成**全序**（R1 修订）：

1. 目录（`folder`）与链接（`link`）在前，文件（`file`）在后；
2. 同组内 `localeCompare(name, 'zh-Hans-CN')`；
3. 仍相等时按名称 UTF-16 码点序兜底（`a < b ? -1 : 1`）。

排序必须在服务端、对**该层全量**完成后再切片，保证：

- 同一份磁盘内容每次返回顺序一致（展开状态才有稳定 key）；
- 分页游标不会因两次请求的排序差异而跳项或重复（B.2 的稳定排序前提）。

链接与目录同组在前的理由：它们是"容器形状的条目"，混在文件中间会让用户以为文件被切开了；
但链接**不可展开**，UI 必须用不同图标区分（B.5）。

### B.5 符号链接与 Windows 重解析点【拟议】

- **不跟随**。符号链接 / junction / 其他重解析点一律不展开、不读取、不写入。
- 以 `kind: 'link'` 叶子节点显示（id 走 `link:` 命名空间，见 B.3），标注原因（"链接不展开，避免越过项目根"）。
- 显示而不隐藏的理由：静默隐藏会让用户以为"文件丢了"。但显示**不等于**授权：`link` 节点不可打开、不可展开、不可预览。
- 服务端**不依赖 UI 自律**：把 `dir` 指向一个链接节点时，服务端 lstat 复核该目录本身不是链接，
  是则 `400 ERR_DIR_IS_LINK`（零 IO 展开、零跟随）。
- 这一条是 B 系列里唯一的"显示但不可用"例外，必须在 UI 与文档里同时写明。

### B.6 目录读取失败的三态【拟议】

| 状态 | 触发 | 响应 | UI |
|---|---|---|---|
| `EMPTY` | `readdir` 成功且 0 项 | `200`，`entries: []`，`nextCursor: null` | "空文件夹"（灰字） |
| `UNREADABLE` | `EPERM` / `EACCES` / `EBUSY` / `EIO` 等目录读取失败 | `403` + `ERR_DIR_UNREADABLE`（不含绝对路径） | "无法读取此文件夹 · 重试" |
| `GONE` | `ENOENT`，或 `ENOTDIR`（该路径不是目录） | `404` + `ERR_RESOURCE_NOT_FOUND` | "该文件夹已不存在" |
| `UNAVAILABLE` | 根身份复核失败 / 屏障期 | `503`；屏障期另可为 `409` | "项目当前不可用" |

**`ERR_DIR_UNREADABLE` 与授权不足必须分开（R1 修订）**：

- `ERR_DIR_UNREADABLE` = **磁盘上这个目录在这一刻读不出来**（权限、占用、I/O）。它是
  "环境事实"，与用户在 WeaveSpace 里的授权状态无关；
- `ERR_PERMISSION_DENIED` = **WeaveSpace 的授权判定拒绝**（项目级读授权缺失、路径越界）。
  它是"策略事实"，换一台机器、换一个用户也一样拒绝。

两者都用 `403` 是 HTTP 语义所限（都是"服务器理解请求但拒绝执行"），但**错误码与用户文案必须分开**：
把"目录读不出来"说成"权限不足"，会诱导用户去重新授权一个其实已授权的项目；
把"未授权"说成"读不出来"，则会掩盖一次真实的越权尝试。因此：

- `ERR_DIR_UNREADABLE` 的公共文案固定为"无法读取此文件夹"，**不得**出现"权限"二字；
- 授权失败沿用 `ERR_PERMISSION_DENIED`，文案固定为"权限不足"；
- 两者都**不得**携带绝对路径。

**禁止把后两种渲染成空目录。** 现有实现正是把它们吞成空（`local-provider.ts:479-482`），属于本轮必须修掉的缺陷。

### B.7 权限边界【拟议】

- **可见 ≠ 可读**。树只暴露名称、相对路径、类型、扩展名。
- 打开正文仍走 `POST /api/open`：G-DISK 门禁（ADR-023）+ 权限判定 + 文本严格解码（非文本返回 `ERR_RESOURCE_NOT_TEXT` / `ERR_ENCODING_UNSUPPORTED`）。
- 保存仍走 `writeConditional`（版本检查 + 根连续性检查点）。
- **执行能力不存在**：Host 没有任何"运行/执行项目内程序"的端点。树里显示 `setup.exe` 不代表能运行它。
- 展示一个节点**不产生**任何授权记录；授权只在 T3 成功时一次性写入。

### B.8 路径展示【拟议】

- 网页端可显示、可复制的只有**项目内相对路径**（如 `docs/readme.md`）。
- 本机绝对路径：不返回、不显示、不提供"复制路径"入口。延续 S-14 / `tests/37 WK-04` 的零泄露断言。
- 系统级拖放与绝对路径查询预留给桌面端；网页端本轮不实现。

## C. 项目列表 UI

### C.1 视觉基准【事实】

以现有 Demo 目录树为唯一基准：`FileTreeRow.tsx` 已固化缩进步长 `TREE_INDENT = 18`、引导线（`tree-trails.ts`）、展开箭头、文件夹/文件图标、选中态、省略规则。**这套原语不改**，只扩展。

### C.2 结构【拟议】

```text
▾ 📁 项目 A                 [可用] [↻]
    ▾ 📁 docs
        ▸ 📁 图片
        📄 readme.md
        📄 设计稿.pdf
    ▸ 📁 空目录
▸ 📁 项目 B                 [不可用]
```

- **项目根就是树的第一级**（`depth 0`），与子文件夹使用**同一个** `TreeRow`；不允许再出现"另一套项目卡片"。
- 多个项目根**并列**显示，各自独立展开、折叠、刷新、重命名、移除。
- 项目根行右侧允许承载状态与操作（状态芯片、刷新、更多菜单），但行本身必须是树行：缩进列、箭头、文件夹图标、名称。

### C.3 现状差距【事实】

| 位置 | 现状 | 差距 |
|---|---|---|

### C.4 状态呈现【拟议】

| 状态 | 根行 | 子层 |
|---|---|---|
| `READY` + 加载中 | 正常 + 行内 spinner | "正在加载…" |
| `READY` + 空 | 正常 | "空文件夹"（不是空白） |
| `READY` + 不可读 | 正常 | "无法读取此文件夹 · 重试" |
| `UNAVAILABLE` | 灰化 + 原因 | 不展示子层；已打开标签与草稿仍保留 |
| `link` 节点 | 斜体/虚线图标 | 无子层，不可打开 |

### C.5 交互契约【拟议】

1. 点击文件行 = 打开（或激活）标签；点击文件夹行 = 展开/折叠（展开时按需加载）。
2. 点击项目根行 = 展开/折叠 **并且** 把该项目设为"当前项目"；切换只改焦点，不清标签、不动草稿。
3. 刷新只作用于**该项目**的缓存，不重置展开状态，不影响其他项目。
4. Demo / Legacy / Multi 三种模式共用同一渲染路径，差异只在数据来源。
5. 折叠整个侧栏（`state.treeCollapsed`）沿用现有行为。

### C.6 本轮不做【拟议】

- 拖放排序 / 拖放移动文件（会变成写操作，需要独立授权设计）。
- 右键菜单体系（重命名磁盘文件、删除文件、在资源管理器中打开）。
- 多选、批量操作、虚拟滚动（单层 2000 上限 + 按需展开，首版不做虚拟化）。
- 搜索/过滤（后续阶段）。

## D. 信任确认

### D.1 两层，且只有一层是安全边界【拟议】

| 层 | 形态 | 作用 | 能否被网页脚本绕过 |
|---|---|---|---|
| **L0 披露** | 前端模态框 | 告诉用户"将要允许什么"，取得**知情** | **能**（脚本可以跳过它） |
| **T3 授权** | Host 进程内本机原生对话框 | 实际选择目录，产生唯一可信的授权证据 | **不能**（只有本机用户能点） |

结论：**模态框是披露层，不是授权层。** 契约必须把这句话写进文档与代码注释，否则下一次改动很容易把模态框当成"确认过了"的依据。

### D.2 严格时序【拟议】

```text
用户点击「添加项目」
  → L0 模态：说明范围与边界
  → 用户点「继续选择文件夹」        ── 取消 ⇒ 结束（零注册/零授权/零磁盘写）
  → GET /api/session-token           （T1 令牌 + 一次性 intentId）
  → POST /api/projects/pick {intentId, acknowledgeScope}  → 202 PENDING
  → Host 进程内弹本机对话框          （T3：唯一人工确认）
      ├─ 取消 ⇒ CANCELLED，零副作用
      ├─ 不可用/超时 ⇒ REJECTED 501，零副作用
      └─ 已选择 ⇒ picked（绝对路径只存在于 Host 内存）
  → inspectProjectRoot 复核（存在/目录/非 UNC/非重解析点/ino 可用）
  → 重复根 / 嵌套根检查
  → ProjectRuntime.addProject({ rootDir: picked, grantSource: 'os-dialog' })
  → ProjectStore 提交（墓碑+配置原子写，ADR-022）
  → 202 → APPLIED；Shell 拉 /api/projects 与 /api/tree 根层
```

强制约束：

1. **模态必须先于 `POST /api/projects/pick`**。禁止"先弹系统对话框、选完再问用户是否信任"——那时目录已被枚举，授权事实上已经发生。
2. 模态关闭/取消**不得**发出任何 pick 请求。
3. 用户在系统对话框取消后，**不得**自动重试或回落到"输入路径"。
4. 整个链路中，绝对路径**永不经过 HTTP**（ADR-021 §3.2 不变量，本轮不放松）。

### D.3 为什么"只加一个前端弹窗"不够【拟议】

只加模态、不加 T3，等于把"网页说用户同意了"当作授权依据：任何能在页面上下文执行脚本的一方都能凭空登记任意目录。反过来，只有 T3、没有模态，虽然安全但用户不知道自己授权了什么。

所以两者**必须同时存在且顺序固定**：模态负责知情，T3 负责证明。

### D.4 文案契约【拟议】

模态出现在**目录尚未选择**的时刻，此时还没有任何真实文件夹名可写进文案。因此：

- 未选目录前，文案只能说"**接下来选择的文件夹**"（或同义的"你即将选择的文件夹"），
  **不得**出现"「<文件夹显示名>」"这种占位符形式，也不得编造一个名字；
- 选完之后的确认/结果界面才可以引用真实名称（该名称来自 Host 侧 `basename`，仍不是绝对路径）。

模态正文必须同时包含三句，缺一不可：

1. **范围**：WeaveSpace 将可以浏览**接下来选择的文件夹**及其所有子目录，并在此范围内读取与保存文件。
2. **边界**：这不代表允许运行其中的程序、自动执行脚本，也不授予 AI 或插件任何额外权限。
3. **可逆**：随时可以从工作台移除该文件夹；移除不会删除磁盘上的任何内容。

### D.5 协议形状【拟议】

`POST /api/projects/pick` 请求体：

```jsonc
{ "intentId": "<一次性>", "acknowledgeScope": "browse-subtree" }
```

- `acknowledgeScope` 缺失或取值不符 → `400 ERR_COMMAND_INVALID`，且**不弹对话框**。
- **它只是协议形状约束，不是授权凭据**：Host 不会因为它存在就授予任何权利，也不会把它写入任何持久记录。真正的授权证据仍是 T3 的 `grantSource: 'os-dialog'`。
- **不得**把 `acknowledgeScope` 描述成"用户已确认"的证明（R1 修订）。它由**网页**填写，
  任何能在页面上下文执行脚本的一方都能构造它；因此：

  | 它**能**证明的 | 它**不能**证明的 |
  |---|---|
  | 客户端实现了披露步骤（协议层可发现跳过） | 有一个真人看过披露文案 |
  | 请求体形状正确（可被测试断言） | 用户点了"继续" |
  | — | 目录已被用户选定 |

- 与之相对，`grantSource: 'os-dialog'` 之所以可信，是因为它**只能**由 Host 进程内在
  T3 成功返回一个真实路径后产生（`runPick()` 是唯一出口），网页无法写入。
  这两者的差别必须在代码注释与 UI 文案里保持，**不许**用前者替代后者。
- 这样设计的目的：让"客户端跳过了披露步骤"在协议层可被发现（测试可断言），同时不给它任何安全语义。

### D.6 取消与失败【拟议】

| 分支 | 项目数 | 授权记录 | 磁盘 | 对话框 |
|---|---|---|---|---|
| 模态取消 | 不变 | 无 | 无写入 | 不弹 |
| 系统对话框取消 | 不变 | 无 | 无写入 | 弹出一次 |
| 选择器不可用 / 超时 | 不变 | 无 | 无写入 | 可能弹出（无结果） |
| 复核失败（文件/UNC/重复/嵌套） | 不变 | 无 | 无写入 | 弹出一次 |
| 提交失败 | 不变（或按 ADR-022 语义） | 无 | 无写入 | 弹出一次 |

### D.7 明确不做【拟议】

- `<input webkitdirectory>`：只给相对文件名，给不出路径，且会诱导用户以为"网页能选目录"。
- 拖放目录注册：拖放不提供绝对路径（ADR-021 F4）；系统级拖放留给桌面端。
- 网页输入绝对路径的兜底入口（永久禁止，不是"暂时不做"）。
