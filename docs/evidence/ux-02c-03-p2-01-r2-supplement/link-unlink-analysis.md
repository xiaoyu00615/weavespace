# `fs.link` + `unlink` 作为移动替代方案的可行性分析

- 项目：WeaveSpace · UX-02C-03-P2-01-R2-Supplement（任务 B）
- 性质：**只做技术研究**。本轮不修改 `moveEntry` / `trashEntry` / `restoreEntry` 的任何移动实现，
  不引入原生依赖。
- 环境：Windows 11（本机）/ NTFS / Node v22.22.2 / 单卷 `C:`，跨卷实验用 `D:`
- 原始实测输出：`link-unlink-raw.txt`（两段脚本，均为真实磁盘操作，非 mock）

> **一句话结论**：`link` 确实提供了 `rename` 没有的**排他目标创建**语义（目标已存在即 `EEXIST`），
> 但它与 `unlink` 组合起来**不是原子移动**，而且会在崩溃窗口里留下"一个 inode、两个名字、
> `nlink=2`"的中间态——这个中间态当前的状态机与身份模型都无法表达。因此本轮**不建议**替换，
> 继续保留 `rename + 排他占位 + fail-closed`。

## 1. 证据分级

本节所有判断都标注来源，四类严格区分：

| 标记 | 含义 |
|---|---|
| **【实测】** | 本轮在本机真实磁盘上跑出来的结果，可在 `link-unlink-raw.txt` 里逐条对上 |
| **【文档】** | Node.js / POSIX / Microsoft 官方文档明确写明的行为（本机未逐条复现） |
| **【推断】** | 由实测 + 文档 + 我们的代码结构推出来的结论，未单独实验 |
| **【未验证】** | 需要别的平台/环境才能确认，本文**不**据此下结论 |

**标准与实现必须分开读**：POSIX 是接口规范，允许"实现自定义"；某个具体内核/文件系统的行为
只能由它的 man page 或实测来支撑。本文凡标注【文档】的跨平台结论，均来自对应平台的 man page，
不是从 POSIX 推断出来的。

## 2. 实测结果（Windows 11 / NTFS / Node 22）

| # | 操作 | 结果 | 证据行 |
|---|---|---|---|
| 1 | `link(src, dst)` | 成功；两个名字 `dev:ino` 完全相同；`nlink` 1 → 2 | `1.src.before/after`、`1.dst.after` |
| 2 | `link(src, 已存在的普通文件)` | **`EEXIST`**，目标内容一字不变（`"occupied"`） | `2.link.onto-exist`、`2.occupied.content` |
| 3 | `unlink(src)` 之后看 `dst` | `src` 名字消失（`ENOENT`）；`dst` 仍在，`nlink` 回到 1，内容完好 | `3.*` |
| 4 | 打开句柄未关闭时 `unlink(该文件)` | **成功**（libuv 以 `FILE_SHARE_DELETE` 打开）；关闭句柄后名字才真正消失 | `4.unlink-with-open-handle`、`E.*` |
| 5 | `link(src, 已存在且被打开的文件)` | 仍是 `EEXIST`（排他性与"目标是否被占用"无关） | `5.link-onto-open-file` |
| 6 | `link(目录, …)` | `EPERM`——目录不能建硬链接 | `6.link-directory` |
| 7 | `link(C:\…, D:\…)` 跨卷 | `EXDEV: cross-device link not permitted` | `7.link-cross-volume` |
| 8 | `rename(a, b)`（`b` 已存在） | 覆盖成功；**`b` 的身份变成 `a` 的身份**（`sameAsA: true`），内容是 `a` 的 | `8.*` |
| 9 | `link` 后不 `unlink`（模拟崩溃） | 两个名字同时存在，`nlink=2`，同一 `dev:ino` | `9.*` |
| 10 | 源文件被打开时 `link` | 成功 | `A.link-while-source-open` |
| 11 | 源是**符号链接**时 `link(src, dst)` | 成功，但 `dst` 与**链接本身**同 `dev:ino`（`nlink` 也 2），真实目标文件 `nlink` 仍为 1 —— Windows 上 `fs.link` **不**穿透重解析点 | `B.*` |
| 12 | 目标父目录不存在 | `ENOENT` | `C.dest-parent-missing` |
| 13 | `link` 是否改动 `mtime` | 不改（`mtimeMs` 前后相同），只有 `nlink`/`ctime` 语义变化 | `D.before/after` |
| 14 | 目标父目录不可写时 `unlink` 失败 | **【未验证】** 当前账户为管理员，`chmod` 不生效，无法在本机构造 | `10.readonly-parent` |

第 8 条对上轮结论的复核：`rename` 在 Windows 上覆盖已存在目标（libuv → `MoveFileExW(REPLACE_EXISTING)`），
且**源对象的身份被搬到目标位置**（`sameAsA: true`）——这正是当前 `payload` 身份核验能成立的前提。

第 11 条值得单独记一笔：**"`link` 会不会穿透符号链接"在标准里没有统一答案**。

- **POSIX（标准规定）**：自 POSIX.1-2008 起，`link()` 的 `path1` 命名符号链接时，
  "是否跟随"被明确写成 **implementation-defined**（实现自定义）——
  既可以解引用，也可以为链接本身建立新链接。更早的 POSIX.1-2001 曾要求解引用。
  可移植的显式控制只有 `linkat()` + `AT_SYMLINK_FOLLOW`（置位=跟随目标，清零=链接链接本身）。
- **Linux（实现）**：自内核 2.0 起**不**解引用——`newpath` 成为指向同一个**符号链接对象**的硬链接。
  man-pages 明确写着这是与 POSIX.1-2001 的偏离，并指出"有些其它实现与 Linux 相同"。
  文件系统层面（ext4/xfs/btrfs）不改变这一点，因为语义由 VFS 的 `link` 路径决定。
- **macOS / APFS（实现）**：相反——`link(2)` 的 man page 写明：
  若 `path1` 的最后一段是符号链接，`link()` 会把硬链接指向**该链接指向的对象**，而不是链接本身。
- **Windows / NTFS（本机实测）**：`fs.link` 不穿透重解析点，`dst` 与链接本身同 `dev:ino`，
  与被指向文件的 `nlink` 无关——第 11 条的实验数据就是这一条。

因此：**不要写"POSIX 默认跟随"或"POSIX 默认不跟随"，两者都是错的**；
正确表述是"POSIX 交给实现，Linux 与 Windows 不穿透、macOS 穿透"。
如果将来要在移动路径上用 `link`，必须先按平台区分，不能假设"反正源一定是普通文件"。
（本轮只在 Windows 上实测；Linux / macOS 的两条结论来自各自 man page，未在本机复现。）

## 3. 九个问题的逐条回答

### 3.1 `link(source, destination)` 是否提供排他的目标创建语义？

**是。【实测 2/5】** 目标已存在（普通文件、空文件、被打开的文件）一律 `EEXIST`，且目标内容不被修改。
这是 `rename` 没有的能力：`rename` 会静默覆盖。就"创建这个目录项"这一步而言，`link` 天然原子。

但要说清楚它排他的是什么：**排他的是"目标名字"**，不是"源对象是不是我们以为的那个"。
`lstat(src)` 核验身份与 `link(src, dst)` 之间，源名字仍可被换成别的对象（同一类竞争窗口，
只是从目标搬到了源）。

### 3.2 是否能避免 `rename` 对已有目标的覆盖？

**在"创建目标"这一步能；作为整体移动不能。【实测 2/8 + 推断】**

- `link` 那一步绝不会覆盖：目标在就直接 `EEXIST`，我们据此拒绝，外部对象毫发无损。
- 但"移动"= `link` + `unlink(源)`，第二步不是原子的：它是对**源名字**的删除，
  与当前 `lstat → unlink` 的清理窗口属于同一类问题（见 R2-Supplement 前的 R2-05 评估）。
- 因此更准确的说法是：**用"原子创建"替换了"覆盖式 rename"，代价是把一个瞬时覆盖窗口换成了
  一个持久的两名字中间态**。

### 3.3 `link` 成功、`unlink` 失败时会留下什么状态？

**【实测 9 + 推断】** 两个名字同时指向同一个 inode，`nlink = 2`，字节内容只有一份。
对用户/上层来说：文件**既在原位置、也在回收区**。

对当前状态机的影响（这是关键）：`reconcileTrash` 的 `pending` 分支只看"payload 是否 present 且身份匹配"，
匹配就 `promote-stored`，**不检查源是否还在**。于是崩溃发生在 `link` 与 `unlink` 之间时，
对账会把记录判成 `stored`，而原路径上还留着同一个文件——用户会看到"删了但还在"，
之后再想恢复又会撞上 `ERR_ENTRY_EXISTS`。

要支持这个方案，必须先给状态机加一个"两个名字都存在且同身份"的判定与清理动作，
而不是像现在这样假设"移动是一个瞬时切换"。

### 3.4 进程在 `link` 与 `unlink` 之间崩溃，如何恢复？

**【推断】** 可恢复，但需要新增显式规则，不能沿用现有对账表：

1. 记录停在 `pending`（意图已落盘、磁盘处于中间态）；
2. 对账看到 `payload` present + 身份匹配 + **源也 present 且同身份** → 这不是 `stored`，
   而是"重复命名"；
3. 恢复动作必须是"删除其中一个名字"（保留 payload、删源，或反之），且删除前要按 `dev:ino`
   复核——这一步又会引入一次 `lstat → unlink` 窗口。

也就是说：崩溃语义从"要么没动、要么已移动"变成"有三种可能，其中一种需要主动清理"。
本轮的任务书明确要求不改动对账与状态机，因此这条足以否掉方案。

### 3.5 `dev:ino` 和 `nlink` 如何变化？

**【实测 1/3/8/9】** `dev:ino` 全程不变（`link` 不改变对象身份，这点与 `rename` 一致）；
`nlink` 在中间态 +1，`unlink` 源之后回到 1。`rename` 则完全不动 `nlink`。

### 3.6 是否会影响当前占位身份核验机制？

**会，而且是负面【推断，基于实测 1】**。当前所有归属判定都是"这个**名字**上的对象是不是我的
`dev:ino`"。硬链接会让**别的名字**也拥有同一个 `dev:ino`：

- `probeReservation` / `sameEntryIdentity` 只看身份，看不出"这个名字上的 inode 已经被别人的名字共享"；
- 唯一能看出共享的信号是 `nlink`，而 `nlink` 恰恰是 R2-04 用来拒绝内部文件（`nlink !== 1` 一律不可信）
  的判据；
- 也就是说：一旦移动路径引入硬链接，`nlink === 1` 就不再是"独占"的可靠证据，
  整个内部文件的信任模型都要重新推导。

当前设计里 `nlink === 1` 是"这个 inode 只被我一个名字持有"的**充要**信号，简单且可测。
引入 link 会把它降级成"至少有一个名字"。

### 3.7 NTFS / APFS / ext4 的行为差异？

| 项 | NTFS（本机） | APFS | ext4 |
|---|---|---|---|
| 文件硬链接 | 支持【实测】 | 支持【文档】 | 支持【文档】 |
| 目录硬链接 | `EPERM`【实测】 | 不允许 | 不允许 |
| 跨卷 / 跨设备 | `EXDEV`【实测】 | `EXDEV`【文档】 | `EXDEV`【文档】 |
| 目标已存在 | `EEXIST`【实测】 | `EEXIST`【文档】 | `EEXIST`【文档】 |
| `link` 对符号链接 | 链接**链接对象本身**（不穿透）【实测】 | **穿透**：指向链接的目标对象【文档：macOS `link(2)` man page】 | **不穿透**：链接链接对象本身【文档：Linux man-pages 2.0+；POSIX 允许两种】 |
| `dev:ino` 稳定性 | 稳定【实测】 | 稳定【文档】 | 稳定【文档】 |
| 网络文件系统（SMB/NFS） | **【未验证】** | — | 可能 `EPERM`/`EOPNOTSUPP`，且 `nlink` 可能不准【未验证】 |

平台差异里最刺眼的是"`link` 是否穿透符号链接"：**POSIX 不做统一规定（implementation-defined）**，
Linux 与 Windows 不穿透、macOS 穿透。当前"源必须是普通文件"的前置校验让这个差异暂时无害，
但它说明**同一段代码在三种平台上可能有两种语义**，需要分支处理，或改用 `linkat(AT_SYMLINK_FOLLOW)` 显式指定。

### 3.8 是否适用于当前 Windows 本机项目？

**技术可行，但只覆盖"同卷的普通文件"，且需要改状态机【实测 + 推断】**：

- 同卷、普通文件：可以（第 1/2/3 条实测）；
- 跨卷：不行（`EXDEV`）——回收区在项目内，天然同卷，所以回收/恢复本身满足；
- 目录：不行（`EPERM`）——而 `moveEntry` 同时服务目录移动，所以**不可能**用它替换 `rename`；
- 长路径/网络盘/只读父目录：**【未验证】**。

### 3.9 是否值得引入？还是保留 `rename + fail-closed`？

**本轮建议保留现有方案。【建议，基于 3.3–3.7】**

理由是收益/代价不对称：

- 收益：消掉"`rename` 覆盖已存在目标"这一个窗口；而该窗口的前提是"外部进程已经能写项目目录"，
  在这种前提下它本来就能直接改用户文件，我们的覆盖并不扩大它的权限（R2-05 已记录）。
- 代价：引入一个**新的持久中间态**（两名字、`nlink=2`），要改对账表、状态机、`nlink` 信任模型、
  平台分支，并新增一类"崩溃后清理"动作；而目录移动仍然只能走 `rename`，
  于是系统里长期并存两套移动语义。
- 结论：这属于"用更大的状态空间换一个微秒级窗口"，不划算。**如果**将来要做，
  前提是先有"重复命名"这个状态，以及针对 `nlink > 1` 的显式语义，而不是顺手替换 `rename`。

## 4. 与现有实现的对照

| 维度 | 现状（`rename` + 排他占位） | 备选（`link` + `unlink`） |
|---|---|---|
| 目标已存在 | 通过 `open(dst,'wx')` 占位 + 复核归属，再 `rename` 覆盖**自己的占位** | `link` 直接 `EEXIST`，无需占位 |
| 覆盖窗口 | 复核与 `rename` 之间（微秒级，已披露） | 无覆盖窗口；但多一个持久中间态 |
| 崩溃中间态 | 无（`rename` 要么发生要么不发生） | 两个名字、`nlink=2`，需要新状态 |
| 源对象身份 | `rename` 保持 `dev:ino`（实测 8） | `link` 保持 `dev:ino`（实测 1） |
| 目录移动 | 支持 | 不支持（`EPERM`） |
| 跨卷 | 回收区同卷，不涉及 | `EXDEV` |
| `nlink` 语义 | 始终 1，可作独占证据 | 中间态为 2，独占证据失效 |
| 符号链接源 | 前置拒绝 | 平台行为不一致（Linux/Windows 不穿透、macOS 穿透；POSIX 未统一） |

## 5. 如果将来引入，最小改动清单（仅备查，本轮不做）

1. 状态机：`pending` 增加"源与 payload 同时存在且同身份"的判定，落成显式状态（如 `duplicated`）
   或"回退为未移动并清理 payload"；
2. 对账表：新增该组合的行，动作限定为"删除其中一个名字"，不得自动删除无法证明归属的对象；
3. 身份模型：`nlink === 1` 从"独占证据"降级，需要另行定义内部文件的可信条件；
4. 平台分支：`link` 是否穿透符号链接按平台区分（Linux/Windows 不穿透、macOS 穿透），
   或改用 `linkat(AT_SYMLINK_FOLLOW)` 显式指定；Linux/macOS 的实际行为需在对应平台补实测；
5. 范围：只用于普通文件的回收/恢复，`moveEntry` 的目录分支继续用 `rename`；
6. 测试：崩溃注入点必须覆盖"`link` 之后、`unlink` 之前"，并断言两个名字的最终收敛结果。

2. SMB / NFS 上 `link` 与 `nlink` 的可靠性。
3. APFS / ext4 上的 `EEXIST`、`EPERM`、`EXDEV` 细节（本文只引 POSIX 与平台 man page，未实测）。
4. Linux / macOS 上 `link()` 对符号链接的实际行为：本文按各自 man page 记录
   （Linux 不穿透、macOS 穿透），**未在对应平台实测**；POSIX 本身只规定"实现自定义"。
   另：Node 的 `fs.link` 在这两个平台上是否与 man page 完全一致，也未实测。
5. `link` 在长路径（> 260）与保留名下的行为。
