# Document Session、保存协议和故障恢复

## 核心规则

1. 同一个 Resource 的多个视图共享权威 Document Session，不各自保存源内容副本。
2. `dirty` 表示内存修改未确认落盘；`SAVE_STARTED`、`SAVE_COMMITTED` 分开记录；AI 文本“已完成”不作为落盘证据。
3. Save 由插件 Serializer 产生数据后调用 Storage `writeConditional(baseVersion)`；检测原文件版本变化则拒绝覆盖并提供 Diff/冲突信息。
4. Local Provider 可以优先写临时文件、fsync（在适用处）、同目录替换和失败清理；不同文件系统/云存储原子性不同，Provider 明确声明保证范围。
5. 严禁由 Parser/Index Job 更新源文件或用户已确认的 Author 数据。
6. 资源变更（修改/移动/删除）先协调打开会话与未保存数据，外部程序变化作为另一个观察事件处理。

## 状态机（简化）

CLEAN → EDITING_DIRTY → SAVING → CLEAN（保存并确认）。

从 SAVING 可进入 CONFLICT / FAILED / OUTCOME_UNKNOWN；后两者不得自动标为 CLEAN。恢复完成后重新验证内容哈希/版本。取消时不丢弃已成功写入的结果。

## 多文件修改

多文件原子提交**不是文件系统默认保障**。采用 Draft Plan → Permission/Version Preflight → Per-file Backups/Staging → Ordered Commit + Receipt → Reconcile；失败时标记 PARTIAL / UNKNOWN，提供受控恢复。不得承诺“所有文件自动回滚必成功”。

## 恢复策略

- 未保存草稿：经用户授权的恢复区（不是普通日志），记录 sessionId、baseVersion、autosaveAt 与受保护内容；默认只在本机保存。
- 突发退出：启动检测未完成操作、进行 reconcile，禁止无证据重放副作用命令。
- 历史：版本/快照和 Git 历史并不相同；不要把 Git Commit 当作文档未保存草稿备份。
- 数据库：SQLite 官方 Backup API 或一致性快照；恢复演练与迁移失败停写是验收条件。
- 单机/多设备：同一项目活跃持久化状态需一个权威 Writer；局域网客户端经 API 调用。

## 文件格式特性

TXT/Markdown 可直接原格式编辑；DOCX/PSD/BLEND 等仅在插件具有可靠 serializer 才允许写回，否则只读预览/另存为。字符位置、BOM、CRLF、编码、Unicode 和二进制格式在各插件中明确声明，不能强制用普通文本替换。

## 禁止事项

- 不经 Session 和权限直接 `fs.writeFile` 写入用户源文件（独立工具/导入场景需另设受控操作）。
- 不使用日志作为写入成功依据。
- 不依据 mtime 单独决定冲突；版本 token 优先。
- 不允许插件卸载时静默抛弃 dirty 状态。
