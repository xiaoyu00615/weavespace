## 一、为什么还有这一轮

R1.1 引入了身份三态（`verified` / `unsupported` / `unverified`），但把
"能力声明"当成了**对象的属性**来用，于是留下两处不对称，加上一处两层归属混判：

| 编号 | 问题 | 真实后果 |
|---|---|---|
| F01 | `treeTargetProblemOf` 只看**目标**是否 `unsupported`，不看**当前**这一侧的身份状态 | 目标声明无能力、当前却能给出锚（或当前根本查不到）时，仍按路径身份放行——"缺锚误放行"换了个入口 |
| F02 | `tree-model.ts` 首屏整层替换时 `identitySupport ?? previous.identitySupport` | 换了 Provider 却继续沿用旧 Provider 的 `unsupported`，新 Provider 白拿一次降级授权；根锚同样被继承 |
| F03 | `DocumentActionsContext.renameProject` 在 `await` 之后只查 `modeRef` 就 `dispatch PROJECT_RENAMED` | `mode` 不是归属凭据：Live→Demo→Live 会回到 `live`，切工作区/推进代次/项目被移除都看不出来 |

对应的验证缺陷：E01（V-15 没有真比较文件内容）、E02（Y-03 容许 null）、
E03（改名没有真正的异步编排测试）。

## 二、任务 A：身份降级必须两侧对称

### 2.1 契约

能力声明描述的是**"这一侧此刻能不能核验身份"，不是"这个对象是什么"**。
因此降级只能发生在**两侧都明确说了"我不能核验"**的时候：

| 目标侧 | 当前侧 | 结果 |
|---|---|---|
| `unsupported`（无锚） | `unsupported`（无锚） | **允许**按路径身份继续（唯一的批准降级） |
| `unsupported` | `unverified` | 拒绝：`无法确认这一行的身份` |
| `unsupported` | `verified`（有锚） | 拒绝：`这一行的身份状态已经变化` |
| `verified`（有锚） | `unsupported` | 拒绝：同上 |
| `verified`（有锚） | `unverified` | 拒绝：`无法确认…` |
| `verified`（有锚） | `verified`（有锚不同） | 拒绝：`这一行对应的对象已经变化` |
| 目标自称 `unsupported` 却带锚 | 任意 | 拒绝：声明自相矛盾 |
| 当前声明 `unsupported` 却给出锚 | 任意 | 拒绝：同上 |

最后两行是"声明与事实打架"：既然能给出锚，说明这一侧其实核验成功了，
`unsupported` 就不可信，不能拿它当降级凭据。

### 2.2 为什么 `verified → unsupported` 也必须拒

直觉上"目标有锚、当前查不到"像是"对象没变但探测失败"，应该放行。
但 `unsupported` 是**能力**声明：如果当前这一侧还能声明"我不支持核验"，
说明它压根没查，而不是"查了但失败"（那是 `unverified`）。
两种都可能，无法区分——于是一律 fail-closed。

**能力变化不得被解释为对象一致**。这是本条的核心。

### 2.3 实现

`treeTargetProblemOf` 先各自归一化两侧身份（`nodeIdentity ?? (nodeAnchor ? 'verified' : 'unverified')`），
再按上表分支；拒绝文案刻意分成三种，因为对用户来说这是三件事：
"查不到"（可以重试）、"变了"（对象换了）、"声明打架"（系统状态异常）。

旧调用者（只传 `currentAnchor`、不传 `currentIdentity`）的行为**没有放宽**：
不传 `currentIdentity` 会被推导成 `unverified`，因此 `unsupported` 目标
必须显式声明 `currentIdentity: 'unsupported'` 才放行。107/108 的老用例
按此补了参数，并各自加了"当前侧 `unverified` 必须拒绝"的反面断言。

## 三、任务 B：首屏不继承能力声明

### 3.1 首屏是替换，不是续页

`tree-model.ts` 的 `applyTreePage` 有两种语义：

- **首屏**（`cursor === null`）：整层替换。这一层的身份能力、根锚、
  每一行的锚全部以**新响应**为准；
- **续页**（`cursor !== null`）：同一批数据的后续分页，可以沿用。

R1.1 的实现对两者用同一个 `??` 合并，于是首屏也继承了。

### 3.2 契约

1. 首屏：`identitySupport` **只取**新响应；新响应没有 → 这一层**没有**能力声明
   （下游按 `unverified` 处理，fail-closed）。
2. 续页：`page.identitySupport ?? previous.identitySupport`（同一批数据内部一致）。
3. 续页声明与既有声明**矛盾** → 整层作废，错误码 `ERR_IDENTITY_STATE_CHANGED`，
   绝不"混合使用"（前半页按 unsupported、后半页按 supported 是最坏的结果）。
4. 根锚 `projectAnchor` 与能力声明同规则：首屏只认新响应，续页才沿用。
5. `projectMeta` 是**刻意的例外**：仍然"第一页带回、续页沿用"。
   理由写在代码注释里——它是纯展示数据（显示名、别名），
   且有 `applyMetadata` 作为权威来源，与"能不能核验身份"性质完全不同。

## 四、任务 C：改名归属分两层表达

### 4.1 两层归属不是一件事

一次项目改名在 Shell 侧有**两个**独立后果：

| 层 | 写什么 | 判据 |
|---|---|---|
| **全局层** | 项目列表里那一行的 `name` | 同一工作区 + 同一加载代次 + 模式未变 + 该行仍在且名字/状态还是发起时那样 |
| **会话层** | 编辑会话（输入行、保存态、报错） | 会话票据未变 + 作用域一致 + 发起时的活动项目仍是活动项目 + 项目仍在 |

旧实现用一个 `modeRef` 同时"保护"两层，这是错的：

- `mode` 不是代次：Live → Demo → Live 之后 `mode` 又是 `live`；
- `mode` 不是工作区：同模式下换工作区，`mode` 不变；
- 两层后果不同：**Host 确实改了名**这件事必须让用户看见，
  哪怕那个编辑会话已经不属于当前上下文。

### 4.2 结果形状

`ProjectRenameResult { outcome, backfill: 'done' | 'stale' | 'nothing', backfillProblem }`

- `outcome` 是 **Host 的实际结果**（`APPLIED` / `REJECTED` / `UNKNOWN`）；
- `backfill` 是 **界面回填情况**（写了 / 过期没写 / 本来就不需要写）。

分开表达的直接目的：**`APPLIED` 不得因为界面切走了就伪装成 `REJECTED`**。
用户看到"改名没成功"去重试，而磁盘上其实已经改了——这是最糟的失败模式。

### 4.3 编排（`apps/shell/src/state/project-rename.ts`）

```
submit()
  ├─ tryLock（单飞：在途时不发第二个请求，也绝不自动重发）
  ├─ projectRenameGateOf(state)           ← 提交前核验一次
  ├─ validateProjectName
  ├─ 名称未变 → 直接关（不发请求）
  ├─ setSaving(true)
  ├─ port.rename()                        ← 发出前已捕获 ownership
  ├─ await
  ├─ projectRenameBackfillProblem（mode → workspaceKey → epoch → 行仍在 → name/status）
  ├─ projectRenameSessionStillCurrent（票据 → scope → activeProject → 项目仍在）
  └─ projectRenameResultEffect → close / keep-error / notice-only
```

要点：

1. **提交前与返回后都核验**。提交前核验防止"已经不该改了还发出去"；
   返回后核验防止"发出去之后世界变了还照写"。
2. **ownership 在发请求之前捕获**，不在 `await` 之后读——后者读到的已经是新世界。
3. 真实名称更新**不受界面活动项目影响**：同工作区内切活动项目，
   `backfill` 照样是 `done`（Z-07 证明）。
4. 切工作区 / 代次变化 / 注册身份变化 → `backfill: 'stale'`，列表不写，
   但 `outcome` 保持 `APPLIED`，并给一条 notice 说明"已更新，原编辑会话已收起"。
5. 旧摘要不覆盖新同 ID 项目：判据里有 `nameAtStart` / `statusAtStart`，
   同 ID 但已被别人改过名的行不会被这次结果覆盖。
6. 禁止自动重发：单飞锁 + 不重试。

### 4.4 为什么抽成纯模块

`.tsx` 无法被 `node:test` import（无 JSX 变换），而 E03 明确要求
"运行实际生产编排逻辑，不能仅测试辅助纯函数或复制生产逻辑作为测试替身"。
抽到 `state/project-rename.ts` 之后，套件 109 的 C 段用的是**真实 reducer**
+ **真实 `createLoadEpoch`** + **deferred promise**，断言的是实际 `dispatch`、
项目列表、编辑会话、提示文案与请求次数——不是模块内部的中间变量。

组件侧只剩注入（`TreeCommandsContext` 的 `renameFlow` 依赖刻意保持 `[actions, dispatch]`，
靠 `stateRef` / `supportedRef` 读实时状态），107 M02 与 108 C05 各有一条源码守卫
断言"组件里不得再抄第二份编排"。

## 五、不变量

1. **能力变化 ≠ 对象一致**：`identitySupport` 的任何变化都不得被解释为身份相等。
2. **首屏不继承**：整层替换时，能力声明与根锚只认新响应。
3. **矛盾即作废**：续页声明打架时整层丢弃（`ERR_IDENTITY_STATE_CHANGED`），不混合。
4. **两层归属分别判定**：全局层写列表、会话层写会话，判据不同、结论可以不同。
5. **`APPLIED` 就是 `APPLIED`**：界面没回填不改变 Host 的实际结果。
6. **不自动重发**：一次提交最多一个请求。

## 七、剩余风险

| 编号 | 风险 | 说明 |
|---|---|---|
| R1.2-R1 | 真·不支持身份的 Provider 必须两侧都声明 | 只有一个旧版 Host 时仍可用（旧版不回声明 → 两侧推导为 `unverified` → 拒绝）。这是 fail-closed 的代价，Shell 与 Host 同版本发布 |
| R1.2-R2 | `identitySupport` 仍是页级声明 | 若将来出现"同一 Provider 内部分行能核验身份"的实现，需要升级到行级 |
| R1.2-R3 | 改名 notice 只在当前界面提示一次 | 不强提醒（无 toast 队列）；用户若恰好切走，只能从项目列表里看到新名字 |
| R1.2-R4 | `probeProjectAnchor` 首屏缺失时的下游后果 | 首屏没有根锚 → 根行 `unverified` → 根行改名被拒（fail-closed）。这是预期行为，但用户会看到"无法确认" |
