## 一、为什么有这一轮

首轮把菜单、工具栏、双击与键盘收敛到一套命令语义上，但双击这条链路上留了四处
"看起来能用、其实不严谨"的地方。它们都不是功能缺失，而是**身份与时间**上的松口：

| 编号 | 问题 | 真实后果 |
|---|---|---|
| R1-01 | `NAME_DOUBLE_CLICK_WINDOW = 200ms` | 普通用户 300–450ms 的连击被判成单击：第一下先打开文件，第二下再改名，改名被自己的会话保护挡住 |
| R1-02 | 仲裁器只通过 `latest.current` 取"最新回调" | 同路径文件被替换时 React 复用组件实例，上一次点击会落到**新对象**上；没有身份，就没有"这已经不是那一行"的判断 |
| R1-03 | `treeTargetProblemOf` 只在"目标有锚 **且** 当前有锚"时比较 | 目标带着锚（=声称知道它是谁）而当前拿不到锚时，跳过比较直接放行；这正是对象被替换且新锚缺失时的空档 |
| R1-04 | 项目显示名编辑会话只在项目从列表消失时清理 | 切工作区/模式后旧草稿还挂着；提交时也不复核归属，旧世界的会话可以提交到新世界 |

这一轮**不新增任何文件系统能力**，只把这四处补成 fail-closed。

## 二、修复前后行为对照

### 2.1 双击窗口（R1-01）

| 场景 | 修复前（200ms） | 修复后（500ms） |
|---|---|---|
| 单击名称，200ms 内没有第二下 | 200ms 时已激活 | 200ms 时**仍在等**，500ms 才激活 |
| 间隔 250ms 双击 | 第一下 200ms 已激活 → 打开文件，随后改名被会话保护拒绝 | 只改名，一次都不激活 |
| 间隔 350 / 450ms 双击 | 同上看 | 只改名 |
| 超出窗口的单击 | 激活一次 | 激活一次 |
| 双击后 | — | 定时器已撤销，`isPending() === false`，不会在窗口末尾再打开一次 |

机制没有变：仍然是"名称区单击延后、图标与行内空白立即激活、键盘 `detail === 0` 立即激活"。
变的只有窗口长度与**每次点击携带的身份**。

代价是诚实的：名称文字上的单击打开最多慢 500ms。这条已记在 `docs/29` 的风险表 C05-R1。

### 2.2 资源身份（R1-02）

仲裁器现在收到的是**发起时的那一份身份**，并且有两个独立的作废层：

```
click(detail=1, identity)  ──►  armed = identity;  timer(500ms)
                                  │
        ┌─────────────────────────┴──────────────────────────┐
        │ 结构性：identity 变 → useMemo 重建仲裁器            │
        │         → useEffect 清理旧实例 → cancel()           │
        └─────────────────────────┬──────────────────────────┘
                                  │
timer 到点 ──► stillSame(armed) ?  onSingle()  :  什么都不做
                                  ▲
dblclick  ──► armed 与第二次点击同源 ? stillSame ? onDouble() : 什么都不做
```

- **身份四元组**：`workspaceKey + projectId + path + anchor`（`ActivationIdentity`）。
  要求"至少涵盖项目、路径、资源锚"，这里额外带上工作区——切工作区后旧意图必须失效。
- **为什么不用 React `key`**：同路径替换时 `key` 不变、组件实例被复用，`key` 恰恰是
  识别不出"换了对象"的那个东西。锚由 Host 的 `dev + ino` 派生，重建才会变。
- **`currentIdentity()` 返回 `null`**（组件正在卸载 / 身份无法确认）时一律**不执行**：
  这是 fail-closed，不是"没有身份就跳过检查"。

> 注意：**原地覆盖写**同一个文件不会改锚（同一个 inode），它仍然是"同一个对象的保存"，
> 打开它是正确行为。只有删除后重建 / 被替换才换身份。真实浏览器取证里用的正是后者。

### 2.3 锚核验 fail-closed（R1-03）

```
目标无锚            → 不进入核验（Provider 无身份能力）          放行
目标有锚 + 当前有锚 → 相等放行 / 不等拒绝「对象已经变化」
目标有锚 + 当前无锚 → 拒绝「无法确认这一行的身份」               ← 本轮修复
```

不误伤的范围：`blank` / `toolbar` / `link` 在函数开头就返回，`project-root` 在锚比较之前返回
（根的身份由 `projectAnchor` 表达，不走条目锚）。

### 2.4 项目显示名会话归属（R1-04）

会话现在带两样东西：`sessionId`（票据）与 `scope`（打开时的模式+工作区模式+工作区摘要）。

| 时机 | 行为 |
|---|---|
| 工作区 / 模式变化 | 未提交会话收起（`scope` 不匹配）；即便留着也提交不了 |
| 切换当前项目 | 会话收起（会话属于具体项目，不跟着焦点走） |
| 项目从列表消失 | 收起（与首轮一致） |
| 提交前 | `projectRenameGateOf` 复核：`scope-changed` → `project-missing` → `unsupported` → `ok` |
| 请求回来 | 按 `sessionId` 核对：仍是当前会话 → `close` / `keep-error`；已不是 → `notice-only` |

`notice-only` 是这一轮特意加的：请求**已经发出去了**，不能因为会话在此期间被收起就把结果
丢掉、假装"什么都没发生"；也绝不自动重发一次。只在状态栏把结果说清楚。

## 三、真实浏览器证据（带实际间隔）

上一轮的 `realDoubleClick()` 是连续派发 `clickCount 1 → 2`，间隔趋近 0——恰好绕过了
"窗口太短"这个问题本身。这一轮改成两次真实点击之间**真的等待**，并用捕获阶段监听器
把浏览器实际产生的事件序列记下来。

`docs/evidence/ux-02c-05-r1-hardening/browser-verification.json`：

```json
"clickSequence300": [
  { "type": "click", "detail": 1, "name": "inner.md", "at": 3414 },
  { "type": "click", "detail": 2, "name": "inner.md", "at": 3729 },
  { "type": "dblclick", "detail": 2, "name": "inner.md", "at": 3729 }
],
"gap300ms": 315
```

- 300ms 与 450ms 两种真实间隔都只改名、不打开文件（截图 `01-slow-dblclick-300ms.png`）；
- 同路径文件被**删除后重建**（锚必变）+ 刷新，期间的在途单击没有打开任何东西
  （截图 `02-same-path-replaced.png`，文档区仍是"还没有打开文档"）；
- 正常单击回归：仍然打开（`03-single-click-opens.png`）；
- 切换当前项目后旧的显示名编辑会话收起，且 `/api/projects/rename` **零请求**
  （`04` / `05` 两张截图）。

**21/21 通过**（真实 Chrome headless + 真实 Host + 独立 Workspace `weavespace-test/c05-r1`）。

## 六、剩余风险

| 编号 | 内容 | 现状 | 处置 |
|---|---|---|---|
| R1-R1 | 名称区单击打开最多慢 500ms | 有意的延迟；图标/空白不受影响 | 若将来要求零延迟，必须先改 UX-02C-02 的"有打开的标签就不能改名"，否则只能改成"双击后撤销已打开"，风险更大 |
| R1-R2 | 双击是否被浏览器判为双击，取决于系统双击阈值（`GetDoubleClickTime()`） | 本机实测 300ms 与 450ms 均被判为双击（`gap300ms=315`、`gap450ms=464`） | 阈值小于 500ms 的系统上，450ms 会退化成两次单击——那是环境语义，不是窗口问题；窗口 500ms 只保证"我们愿意等"，不能强迫浏览器合并 |
| R1-R3 | 项目根名称单击（切换/展开）也被延后 500ms | 与文件行同一套仲裁 | 若体感明显，可后续只对"有改名入口的行"保留延迟；本轮不改，避免两套语义 |
| R1-R4 | `ProjectList` 里根的 `activationIdentity` 依赖 `projectAnchor`，锚晚到时可能让在途单击作废 | 锚随根层首屏一起返回，实际未观察到 | fail-closed 的代价，宁可少打开一次 |
| R1-R5 | 会话结果 `notice-only` 只写状态栏 | 已发出请求不会被"伪装成未发送" | 若将来要"后台结果可回看"，需要真正的操作日志，属 ARCH-01 |
| R1-R6 | `TreeToolbar` 仍自算 `usable`（`projectId` / `hiddenCount`） | 可用性判断本身取自矩阵，重复的只是"入参" | **ARCH-01 待办**，本轮按范围限制不动 |

## 七、模块职责（本轮增量）

```
state/tree-commands.ts
  ActivationIdentity / activationIdentityOf / sameActivationResource / activationIdentityKey
                                      资源身份：工作区 + 项目 + 路径 + 锚
  createActivationArbiter             每次点击带身份；到点与落槌前各核一次；身份未知即不执行
  NAME_DOUBLE_CLICK_WINDOW = 500
  workspaceScopeOf                    会话所属世界（模式 + 工作区模式 + 工作区摘要）
  projectRenameGateOf / …Message      提交前的归属复核与文案
  projectRenameResultEffect           请求回来后：close / keep-error / notice-only
  treeTargetProblemOf                 锚核验改为 fail-closed

components/FileTreeRow.tsx
  接收 activationIdentity；identity 变化即重建仲裁器（旧实例由清理函数 cancel）；
  click/doubleClick 都显式传身份

components/TreeBranch.tsx / ProjectList.tsx
  为每一行（文件 / 文件夹 / 项目根）构造身份，锚取该行的 node.anchor / projectAnchor

components/TreeCommandsContext.tsx
  会话带 sessionId + scope；三条收敛 effect；提交前 gate、提交后按票据落地
```

没有新增状态管理框架，没有第二套改名链路（`actions.renameProject` 全文仍只有一处调用）。
