## 一、为什么还有这一轮

R1 把"窗口 / 身份 / 锚 / 会话"四处补上了，但复查发现四处**边界**仍然松：

| 编号 | 问题 | 真实后果 |
|---|---|---|
| R1.1-A | 身份变化后 `FileTreeRow` 重建仲裁器，新实例 `armed = null`；`click(detail ≥ 2)` 仍然接受事件并把它记成新的 `armed` | 旧手势的**残响**（浏览器还在数连击）被当成新手势起点，随后 `dblclick` 给**新对象**改名 |
| R1.1-B | `anchor === null` 同时表示"Provider 不支持身份能力"和"这次身份探测失败" | 本地真实项目里探测失败 = 路径身份匹配成功：菜单命令与双击都放行 |
| R1.1-C | 项目改名结果只按 `sessionId` 核对"会话是否还在" | 请求在途时切项目/切工作区，清理是 `useEffect`、fetch 回调是微任务，回调可能先跑；旧结果被写进"看起来还当前"的会话 |
| R1.1-D | 上述修复容易把正常交互一起打死 | 500ms 单击、正常双击、键盘、图标/空白、项目根都必须原样工作 |

本轮**不新增任何文件系统能力**，也不改 Host 的授权与身份核验机制。

## 二、任务 A：仲裁器重建后的手势归属

### 2.1 契约

一段"单击或双击"手势必须满足三条：

1. **起点在本仲裁器内**：`detail ≥ 2` 只有在 `armed !== null`（本实例收到过第一次点击）时才有效；
2. **同源**：第一次与第二次点击必须是同一个 `ActivationIdentity`（含身份状态）；
3. **不重绑**：第二次点击绝不把 `armed` 改写成自己带来的身份。

任何一条不成立，整段手势作废（`clear()` + `armed = null`），且**不**顺手武装一个定时器。

### 2.2 实现

- `click(detail, identity)`：`detail ≥ 2` 且 `armed === null` → 直接 `clear(); return;`（不设 `armed`）；
- `armed !== null` 但 `!sameActivationResource(armed, identity)` → 整段作废；
- 同源时只撤掉在途单击，**保留** `armed` 供 `dblclick` 落槌（不再 `armed = identity`）；
- `FileTreeRow` 在**渲染期**（`useMemo` 体内）取消被替换的仲裁器实例，不再只依赖 `useEffect` 的 cleanup：
  cleanup 在提交后才跑，中间那一下正好是残响的窗口。

### 2.3 为什么不能用 React key

同路径替换时 `key` 不变、组件实例被复用——`key` 恰恰识别不出"换了对象"。
身份必须来自 Host 核验出的锚（`dev:ino` 派生），R1.1 再把**身份状态**并进等式。

## 三、任务 B：身份三态

### 3.1 数据链（调查结论）

```
Host /api/tree
  ├─ markMetadata(probe = treeProvider).identityOf(relPath)
  │     ├─ 返回 dev:ino  → 生成 anchor（sha256 前 32 位）
  │     ├─ 返回 null     → 对象已消失
  │     └─ 抛异常        → 探测失败
  └─ buildTreePage(entries, { anchors, identitySupport })
        ↓  TreePageDto.anchors / identitySupport
client-api.listTree → TreeQueryOutcome.anchors / identitySupport
        ↓
tree-model.TreeLevelState.anchors / identitySupport（续页沿用，不清空）
        ↓
TreeBranch：activationIdentityOf({ …, anchor, support })
        ↓                       ↘
FileTreeRow（仲裁器）        TreeCommandTarget.nodeIdentity（菜单失效检测）
```

关键点：**能力由 Host 在页级声明**（`typeof provider.identityOf === 'function'`），
不由"这一页没有锚"反推。`unsupported` 因此只能来自声明，异常不会自动变成它。

### 3.2 三态定义

| 状态 | 条件 | 语义 | 允许的动作 |
|---|---|---|---|
| `verified` | 有非空锚 | 已核验，知道它是谁 | 锚必须一致；否则拒绝 |
| `unsupported` | 无锚 **且** Host 声明 Provider 无身份能力 | 唯一被批准的降级：按项目 + 路径身份 | 放行（不伪造锚） |
| `unverified` | 无锚且有能力，或未声明能力 | 探测失败 / 对象消失 / 无法确认 | **一律拒绝**（fail-closed） |

### 3.3 判定

- `identityVerificationOf({ anchor, support })`：唯一推导入口；
- `ActivationIdentity.verification`：身份的一部分，进入 `activationKeyOf`；
  `stillSame` 对 `unverified` 直接返回 `false`（不做"路径相同所以还是它"的推断）；
- `treeTargetProblemOf`：目标 `unverified` → 拒绝；目标 `unsupported` → 放行；
  目标 `verified` → 当前侧必须 `verified` 且锚相等，否则拒绝。

### 3.4 不误伤的上下文

`blank` / `toolbar` / `link` / `project-root` 在身份检查之前就返回 `null`：
它们没有"磁盘条目身份"可比。项目根行的仲裁器只在拿到根令牌（`projectAnchor`）
时装配——没有根令牌就退回"点了就切"的即时行为，不伪造一个 `unverified` 把根行打死。

## 四、任务 C：项目改名的异步归属

### 4.1 为什么 `sessionId` 不够

```
用户点提交 → await renameProject()
用户切项目 → setState（activeProjectId）
                     ↓ React 提交后才跑 useEffect → setProjectRename(null)
fetch 回来（微任务）→ 此时 renameRef 仍是旧会话、sessionId 仍相等 → 误判"还当前"
```

### 4.2 三条同步核对

`projectRenameSessionStillCurrent({ session, sessionId, currentScope, activeProjectId })`：

1. `session.sessionId === sessionId`（不是新会话）；
2. `session.scope === currentScope`（同一模式/工作区，用 `scopeRef` 同步读）；
3. `session.activeProjectAtStart === activeProjectId`（会话开始时与此刻的活动项目相同）。

任一条不成立 → `projectRenameResultEffect` 返回 `notice-only`：

- 已发出的请求**不被伪装成未发送**（给出明确提示）；
- **不写回**任何编辑会话（包括刚打开的新会话）；
- **不自动重试**。

`activeProjectAtStart` 与 `projectId` 是两件事：右键菜单可以给**非当前项目**改显示名，
所以不能直接比较 `session.projectId === activeProjectId`。

## 六、明确的不变量

1. **不引入客户端自述身份**：`identitySupport` 是 Host 对自身能力的声明，
   锚仍由 Host `lstat` 派生并只用于比对；两者都不构成授权凭据。
2. **`unsupported` 不可推导**：只能由 Host 声明；缺少声明一律 `unverified`。
3. **`unverified` 不参与相等推断**：任何延迟意图都不执行。
4. **一次手势只属于一个身份**：残响不会被重新绑定成新手势。
