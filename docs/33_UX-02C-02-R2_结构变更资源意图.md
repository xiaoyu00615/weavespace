# UX-02C-02-R2：结构变更的资源意图契约

> 父提交：`92a2565922a31c14037f659627a24ff839af7baa`（UX-02C-05-R1.2）
> 分支：`wip/ux-02c-02-r2-resource-intent-20261127`
> 本文只描述 R2 相对 UX-02C-02 / R1 / R1.1 / R1.2 的**增量**。
> 结构变更的编排顺序与屏障语义以 `docs/24`、`docs/25` 为准；
> 资源锚与身份三态的定义以 `docs/31` 为准；身份降级对称性以 `docs/32` 为准。

## 一、这一轮修的是什么

UX-02C-02 的结构变更（改名 / 移动）一直是**按路径**动手的：Shell 说"把
`docs/notes.md` 改成 `数学笔记.md`"，Host 授权这条路径，Provider `rename` 这条路径。
路径在三个时刻可能指向**不同对象**：

1. 用户右键那一刻（Shell 记住的是"这一行"）；
2. 用户敲完新名字按 Enter 那一刻（可能已经过了几十秒）；
3. Provider 真正调用 `rename(2)` 那一刻（占位建立之后还有一段窗口）。

契约缺口不在"有没有校验"，而在**三层各自都以为别人知道要改哪个对象**：

| 层 | 旧行为 | 后果 |
|---|---|---|
| Shell | 只记 `projectId + sourcePath + 新名字` | 输入期间外部替换了同名文件，提交时仍然照发 |
| Host | 只按路径授权 + 屏障，不接收任何"预期源对象" | 无法判断这是不是一个已经被换掉的对象 |
| Provider | `moveEntry(source, dir, name)` 只按路径 `rename` | 磁盘上的对象是谁无关紧要，谁在这个路径上就搬谁 |

于是出现一条非常糟的链路：用户看着 `a.md`（旧对象）点改名 → 别人（同步工具、
脚本）把它删了重建 → 用户按 Enter → **界面上的 `a.md` 被搬走，内容却是新对象的**。
用户以为自己改的是旧文件的名字，实际上动的是别人的文件。

R2 的修法不是"多加一道校验"，而是把"用户想改哪个对象"变成一条**贯穿三层的显式参数**：

```
Shell 冻结意图（锚）→ 请求体带 sourceAnchor → Host 与当前身份比对 → 传给 Provider
→ Provider 在副作用之前 / 之中各核对一次
```

任何一层拿不到这个参数，都**必须拒绝**，不得退化成"按路径凑合"。

## 二、资源意图（`StructureIntent`）

### 2.1 形状

```ts
interface StructureIntent {
  readonly projectId: string;
  readonly sourcePath: string;      // 相对项目根，POSIX 分隔
  readonly entryKind: 'file' | 'directory';
  readonly anchor: string;          // 从行上取到的 32 位锚（不是现算的）
  readonly verification: 'verified' | 'unsupported' | 'unverified';
  readonly sessionId: number;       // 这一次打开对话框/输入行的会话票据
}
```

`anchor` 必须来自**打开意图那一刻行上已有的锚**，不允许在提交时重新从
`/api/tree` 现取——现取等于"用最新的对象替换用户的意图"，正是要修的那个 bug。

`sessionId` 由 Shell 单调递增分配，只用于"结果回来时是不是还该写回这个界面"，
不参与任何授权或身份判定。

### 2.2 捕获即拒绝（比"打开文件"更严）

| 行的身份状态 | 打开改名框 / 移动框 | 理由 |
|---|---|---|
| `verified` + 有锚 | 允许 | 唯一可提交的状态 |
| `unsupported` | **拒绝**：`这一行的身份无法核验` | 见下 |
| `unverified` / 无锚 | **拒绝**：`无法确认这一行的身份` | 连"是谁"都不知道 |

这里的严格度**故意比 `docs/32` 的身份降级更严**：`docs/32` 允许"目标与当前两侧
都明确 `unsupported`"时按路径打开文件——因为打开是只读的，最坏结果是显示错内容，
再读一次就好。而结构变更会**真的动磁盘**：搬错对象、覆盖别人的文件都是不可逆的。
所以能力声明为 `unsupported` 的 Provider **在结构变更上没有任何降级通道**，
只给一句明确的拒绝。

### 2.3 提交前的再核验

Shell 在发请求**之前**用当前层表再核验一次（`structureIntentProblem`）：

| 当前行状态 | 结果 |
|---|---|
| `verified` 且锚相同 | 放行 |
| `verified` 但锚不同 | `这一行对应的对象已经变化，命令没有执行` |
| `unverified` | `无法确认这一行的身份，命令没有执行` |
| `unsupported` | `这一行的身份状态已经变化，命令没有执行` |

这一道只减少无谓请求，**不是**权威判据：客户端看到的树可能本身就已经过期。
权威判据始终在 Host（它有磁盘）。

## 三、Host 契约：`POST /api/files/rename|move`

### 3.1 请求体新增字段

```jsonc
{
  "projectId": "…",
  "sourcePath": "docs/notes.md",
  "targetParentDir": "docs",   // move 才有
  "name": "数学笔记.md",
  "sourceAnchor": "0123456789abcdef0123456789abcdef"   // 新增，必填
}
```

`sourceAnchor` 的校验顺序（全部**零 IO**）：

| 情况 | 结果 |
|---|---|
| 未提供 / `''` / 纯空白 | `400 ERR_STRUCTURE_INTENT_MISSING` |
| 形状不是 `^[0-9a-f]{32}$` | `400 ERR_COMMAND_INVALID` |

形状校验发生在**消费一次性 intentId 之前**：形状非法不该消耗掉用户的授权票据。

### 3.2 编排顺序（在原有顺序中插入两处）

```
1. 形状校验（零 IO）
2. 授权：源 + 目标
3. withStructureChange 屏障
4. 会话保护（活动 View / 草稿）
5. 【新】Provider 是否具备身份能力 → 否则 409 ERR_ENTRY_IDENTITY_UNVERIFIED
6. 【新】读源身份 identityOf(sourcePath) → null 则 404 ERR_RESOURCE_NOT_FOUND
7. 【新】用 metadataAnchorOf 派生预期锚并与 sourceAnchor 比对 → 不等则 409 ERR_ENTRY_SOURCE_CHANGED
8. withStructureDiskOp → provider.moveEntry(source, dir, name, identity)
9. 结果保留 MOVED / REJECTED / UNKNOWN
```

第 7 步**必须复用 `apps/server/src/metadata.ts::metadataAnchorOf`**，不另写一套：
派生规则一旦出现第二个实现，"同一个对象算出两个锚"就会变成无法解释的误拒。

### 3.3 领域错误与 HTTP 映射

| 错误码 | HTTP | 含义 |
|---|---|---|
| `ERR_STRUCTURE_INTENT_MISSING` | 400 | 没有身份预期 |
| `ERR_COMMAND_INVALID` | 400 | 锚形状非法 |
| `ERR_ENTRY_IDENTITY_UNVERIFIED` | 409 | Provider 无身份能力（不得降级为路径操作） |
| `ERR_ENTRY_SOURCE_CHANGED` | 409 | 路径上的对象不是预期那一个 |
| `ERR_RESOURCE_NOT_FOUND` | 404 | 源已经不存在 |

`ERR_ENTRY_SOURCE_CHANGED` 此前只出现在回收区的映射表里，**主映射表缺失**，
会被默认成 500——本轮补齐。

## 四、Provider 契约

### 4.1 签名

```ts
moveEntry?(
  sourcePath: string,
  targetParentDir: string,
  targetName: string,
  expectedIdentity: string,   // 新增，必填
): Promise<MoveEntryResult>;
```

`expectedIdentity` 是 Provider 自己的身份格式（本地实现为 `${dev}:${ino}`），
不是资源锚。Host 派生锚用于跨层比对，Provider 用自己的格式再核对一次——
两者不是重复劳动：前者防"Shell 的意图过期"，后者防"占位期间对象被换掉"。

### 4.2 两处核验

| 位置 | 目的 | 失败结果 |
|---|---|---|
| 解析源元数据之后、**任何副作用之前** | 证明零副作用 | `ERR_ENTRY_SOURCE_CHANGED` / `ERR_RESOURCE_NOT_FOUND` |
| **`rename` 调用之前**（占位已建立） | 覆盖占位窗口内的外部替换 | 见 4.3 |

第一处失败时**连排他占位都不建立**：事后清理干净 ≠ 从未建立，测试用
`afterMoveReserve` 钩子把"占位次数"当可观测点钉住了这一点。

### 4.3 第二处失败时的占位归属

| 占位状态 | 结果 |
|---|---|
| `missing`（我们还没建） | `REJECTED` + 对应错误码 |
| `owned`（仍然是我们建的） | 清理占位后 `REJECTED` |
| `owned` 但清理失败 | `UNKNOWN`（磁盘状态不可宣称） |
| `foreign`（已被外部替换） | `UNKNOWN` —— **绝不删除别人的东西** |

### 4.4 不宣称的事

`dev:ino` **不是**绝对的对象身份证明：inode 会被复用，跨平台语义不一，
`dev` 在部分文件系统上不稳定。契约只说"在本次核验时刻，这个路径上的对象
与预期不是同一个"，不说"这两个时刻一定是同一个对象"。因此：
所有拒绝都是**保守的拒绝**（宁可误拒不可误改），而所有成功都不宣称长期不变。

## 五、元数据与隐藏记录（B5）

> **R2.1 更正（2026-11）**：本节原表述"结构变更**不迁移**任何挂在旧路径上的
> 记录"是**错的**，已按实际实现更正。真正不迁移的是"拒绝之后"和"对象已经换了"；
> 改名/移动**成功**时，标注（标注名/标签/颜色）会随文件迁移到新路径
> （UX-02C-04-R1）。隐藏记录仍是原有语义（它属于路径可见性，不属于对象）。
> 详见 `docs/34_UX-02C-02-R2.1_结构变更异步归属.md`。

四种情形必须分开表达，它们的结论**不同**：

| 情形 | 标注（标注名/标签/颜色） | 隐藏记录 |
|---|---|---|
| **成功**（源锚已核验、磁盘变更完成） | 随路径**迁移**到新路径；旧路径不再有记录（`metadataMigration: 'moved'`） | 仍挂旧路径，状态如实变为 `missing`（隐藏是路径可见性，不随对象搬家） |
| **成功但标注没写进去** | `metadataMigration: 'failed'`：**磁盘已经变了**，只是配置没写进去；界面必须同时说清"文件已移动"和"标注未能迁移" | 同上 |
| **拒绝**（源已变/目标冲突/授权不足） | 不迁移、不继承、不静默删除 | 不变 |
| **对象已被外部替换**（锚不符） | 旧标注**不**跟到新对象上；新路径 `meta` 为空 | 新对象不继承"已隐藏" |

两条纪律：

1. **磁盘成功与标注迁移是相互独立的两个结果**。`metadataMigration: 'failed'`
   不等于改名失败——磁盘那一步已经生效。把它说成失败，用户会去重试一次真实操作
   （那时源路径已经不存在），或者以为文件没动。
2. **迁移的前提是"锚核验通过的那个对象"**。跟着名字走的迁移会把别人写的东西
   贴到另一个文件上；因此迁移只发生在源身份已被核验、且目标身份已被核验的路径上。

隐藏记录为什么例外：它描述的是"这个路径在工作台里是否显示"，不是"这个对象叫什么"。
改名后旧路径的隐藏记录失效（`missing`），这是如实表达，不是丢数据。

## 六、拒绝之后：层表必须被判为过期

`ERR_ENTRY_SOURCE_CHANGED` / `ERR_RESOURCE_NOT_FOUND` 不只是"命令没执行"，
它同时是一条**磁盘事实**：层表里这一行挂着的锚已经过期。

`StructureRunnerHost.onRejected` 把这个事实交回 Shell，Shell 只做一件事：
**重取源所在的那一层**（不递归、不动其它层、不清草稿），于是行上的锚更新，
用户重新选中当前对象即可正常改名/移动。

为什么必须有这一步：工具栏「刷新当前目录」的目标是
`toolbarTargetOf(activeProjectId)`，**不带路径**，永远只重取项目根层。
嵌套文件（如 `docs/notes.md`）被外部替换后，没有任何界面途径能把那一层的旧锚刷掉，
用户重试多少次都会被同一个旧锚挡住——变成一个**永久卡死**的行。

`onRejected` 只上报事实（错误码 + 目标），是否重取由 Shell 决定；
`UNKNOWN` 不上报（不确定的事情不能当成"已经变了"），本地阻断/缺锚也不上报。

## 七、不变量

1. 任何声称"成功"的改名/移动，都必须有**一份在打开意图时就存在的锚**参与。
2. 任何一层拿不到锚、锚形状非法、锚不匹配，都必须拒绝，**不得**退化为路径操作。
3. 拒绝必须保证**零副作用**：源不动、目标不出现、占位要么未建立要么清理干净。
4. 只有能证明零副作用才允许 `REJECTED`；证明不了就是 `UNKNOWN`。
5. `UNKNOWN` 不自动重试、不重发、不据目标存在推断成功。
6. 拒绝后旧记录不迁移、不继承、不静默删除。
7. 成功时标注只在"源身份与目标身份都已核验"的路径上迁移；隐藏记录属路径可见性，
   仍按原有语义留在旧路径并如实变为 `missing`。
8. 磁盘变更成功与标注迁移失败是**两个独立结果**，不得互相改写。

## 八、剩余风险

| 编号 | 风险 | 说明 |
|---|---|---|
| R2-R1 | `dev:ino` 复用 | inode 号被系统复用后，"同锚"可能指不同对象。缓解：锚还绑了 `projectId + pathKey + rootToken`，且窗口极短；未消除。 |
| R2-R2 | 两处核验之间仍有 TOCTOU | 第二处与 `rename(2)` 之间是原子窗口之外的最后一次读。缓解：拒绝优于误改；未消除。 |
| R2-R3 | 网络文件系统 / 容器挂载 | `dev` 与 `ino` 的稳定性依赖本地文件系统，SMB/NFS 上不保证。 |
| R2-R4 | 会话焦点（既有） | 提交期间输入框 `disabled` 会夺走焦点，结果回来后不重新聚焦，此时 Escape / Enter 无人接收；对话框的 Escape 处理还要求焦点在对话框内。这是**R2 之前就存在**的交互细节（`InlineCreateRow` / `MoveEntryDialog` 本轮未改），已作为事实记入浏览器证据。**状态：R2.1 已关闭**（`docs/34` §E，`apps/shell/src/components/focus-restore.ts`），本节保留历史记录不改写。 |
