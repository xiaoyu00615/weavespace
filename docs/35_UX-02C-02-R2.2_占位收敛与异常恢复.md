## 一、F01：占位残留的结果语义（最高优先级）

### 缺陷

Provider 建立排他占位（0 字节文件）之后，如果目标父目录被外部**整体移走**并
在同路径建了新目录，旧实现的判定链是：

1. 10d `targetDirStillMatches()` = false；
2. `rejectSourceChanged('ERR_ENTRY_TARGET_CHANGED')`；
3. 内部 `reservationState()` 读的是**新目录里的同名路径** → `missing`；
4. 结论 `REJECTED`（"零副作用，可以放心重试"）。

但真实磁盘上，占位 `archive/a.md` 正躺在 `archive-old/` 里（F-08 的实测事实）。
**REJECTED 在这里是假的**：它声称没有留下任何副作用，而我们的占位还在用户的目录里。

### 修正

结果语义按"占位是否已经建立"分叉：

| 情形 | 结论 | 理由 |
|---|---|---|
| 未建立占位，目标目录身份已变（`ERR_ENTRY_TARGET_CHANGED`） | `REJECTED` | 零副作用可证明，用户可以重选目标重试 |
| 已建立占位，目标目录身份已变（10b / 10d / 源终检任一路径） | `UNKNOWN` | 占位跟着目录走了，去向与收敛都不可证明 |
| 已建立占位，目录连续、占位仍是 `owned` | `REJECTED` + 清理占位 | 可证明零副作用（先 `unlink` 再返回） |
| 已建立占位，目录连续但占位被外部换成 `foreign` | `UNKNOWN` | 绝不删外部对象，也无法证明收敛 |

配套三条纪律：

1. **从不扫描项目去找占位**。占位可能在任何一个被移走的目录里，挨个找等于遍历用户磁盘；
2. **从不删除移动后目录中的对象**。那是用户的目录，不是回收区；
3. **目标目录身份变化后，禁止在新同名目录中重新建立占位**。10b 与 10d 的重新占位
   分支都先认目录，再认占位——顺序反了就会在用户从未确认过的目录里留下痕迹。

### 代码落点

- `packages/storage/local-provider.ts`
  - 10b：`if (!(await targetDirStillMatches())) return unknown();` 位于 `reservationState()` **之前**；
  - `rejectSourceChanged()`：占位已建立时先核目录连续性，不成立直接 `unknown()`；
  - 10d：`return reserved ? unknown() : reject('ERR_ENTRY_TARGET_CHANGED')`；
  - 10d 的重新占位分支因此只会在"目录已核验"之后执行。

## 二、F02：目标身份变化后的恢复

### 缺陷

`ERR_ENTRY_TARGET_CHANGED` 只被显示成一条错误：层表里那个文件夹行仍挂着**过期锚**，
对话框也仍握着**冻结的旧锚**。用户唯一出路是关掉对话框重开——而重开并不保证他会做，
也不保证重开后读到的是新身份。

### 修正

1. **按世界票据重取"目标所属父层"**：`refreshStructureTargetParent`。
   - 目标 `archive` → 重取根层（锚在根层 `anchors['archive']`）；
   - 目标 `a/b` → 重取 `a` 层；
   - 目标 `''`（项目根）→ 重取根层（根锚是 `projectAnchor`）；
   - 跨工作区/跨代次 → 闸门作废，**零请求**。
2. **不自动替换冻结锚**：只把对话框标记为 `targetStale`（"目标身份已过期"）。
3. **显式入口**：对话框出现「重新确认目标」按钮；点击才重新捕获身份并清掉标记。
   重新选同一个路径不会触发 `<select>` 的 change，所以这个入口是必需的。
4. **重新确认前不得自动提交**：过期状态下按 Enter / 点确认，本地挡住并提示
   "请先点「重新确认目标」再提交"，零请求。
5. **不重发已拒绝的请求**：拒绝就是终止，恢复只能由用户的下一次明确操作触发。

### 真实浏览器证据

`browser-verification.json`：打开 → 选 `docs` → 外部删除重建 `docs` → 提交被拒
（`目标文件夹已被外部替换，未执行任何移动（请重新选择目标）`）→ 父层被重取 →
出现「重新确认目标」→ 过期状态下按 Enter 不发请求 → 点重新确认 → Enter 提交成功。
两次请求的 `targetAnchor` 分别是 `f43fb961…` 与 `057689b3…`（不同），
第一次请求源文件 inode / SHA-256 不变、目标未创建，全程只有 2 次 move 请求。

## 三、F03：UNKNOWN 提示的真实性 + 会话写入守卫

### 提示

旧文案无条件写"已只读刷新源位置与目标位置"。而只读核对有三种真实结局：

| `checkLocations` 结论 | 提示 |
|---|---|
| `applied` | 已只读刷新源位置与目标位置，请人工核对（不会自动重试、不会自行回滚） |
| `stale`（世界已换，闸门挡下） | 当前界面已经切换，**没有执行**只读核对，请手动刷新后核对 |
| `failed`（抛错/未完成） | 只读核对**没有完成**，请手动刷新后核对 |

三种都不承诺自动重试；核对失败**不会**触发结构变更重发。Host 的 `UNKNOWN`
语义原样保留（`status` 仍是 `UNKNOWN`，不因提示文案改变判定）。

### 会话写入守卫

结果回来时，界面可能已经换了会话（对话框被关闭又对另一行重开）。旧实现先用 ref
读一次"还是不是我"，再 `setState(null)` / `setState({...submitting:false})`：
两次读之间新会话可能已经挂上，旧结果会改写**新会话**的错误位、提交状态，
甚至把它关掉。

现在三种写回（写错误 / 改提交状态 / 收起会话）都经过
`updateSessionIfOwned(current, sessionId, sessionIdOf, update)`：

- `current === null` → 不复活；
- 票据不符 → 原样返回（一个字段都不改）；
- 票据相符 → 才执行更新（`update` 返回 `null` 时才收起）。

不建立第二套会话框架：票据仍是 `StructureIntent.sessionId`，判据仍是
`structureSessionApplies`。

## 四、不变量（在 R2.1 之上新增/收紧）

1. 占位一旦建立，"零副作用"就不再是可以随口宣称的结论：证明不了 → `UNKNOWN`。
2. 结果语义按"占位是否已建立"分叉，不按"当前路径上有没有同名文件"推断。
3. 重新占位前必须核验目标父目录身份；目录变了就不许在新目录里留下任何东西。
4. 目标身份被拒 → 重取目标所属父层（按世界票据）；跨世界零请求。
5. 恢复只能由用户显式动作触发：不自动换锚、不自动提交、不自动重发。
6. `UNKNOWN` 的提示必须与实际核对结局一致。
7. 结果只能写进发起它的那个会话；票据核验在函数式更新器内部完成。

## 七、R2.2-PATCH：两处生产链路缺口

> 基线 `5d1c161`（R2.2）。这一节只记录 P01、P02 两处修补，其余结论（§一~§六）不变。
> 上一节不变量 1/2/3/6 的措辞依旧成立，但**适用范围**由本节修正。

### P01：Provider 内部的父目录基准

#### 缺陷

`targetDirStillMatches()` 的第一行是：

```ts
if (expectedTarget === null) return true;
```

`expectedTargetIdentity` 只有"用户在移动对话框里显式选了目标"时才会传。**普通改名**
（`docs/a.md` → `docs/b.md`）与**项目根目标**（`targetDir = ''`）都不传，于是：

- §一写的"10b/10d 先认目录、再认占位"在改名路径上**一条都没生效**；
- 改名建立占位后父目录被整体移走，10b 会认为目录没变 → 在新同名目录里**重新占位**；
- 源终检随即发现源不在新目录 → 走 `rejectSourceChanged` → 又因为"目录没变"而
  在新目录里把占位删掉 → 返回 `REJECTED`。
- 用户看到的是一句"零副作用"，而旧目录里那个 0 字节占位从来没人处理过。

根因不是"少写了一个判断"，而是**基准的来源只有一个**：调用方给了才有。

#### 修正：基准有两层来源

```ts
const expectedTarget = /* 调用方给的预期，没有就是 null */;
let targetBaseline: string | null = expectedTarget;
const targetDirStillMatches = async (): Promise<boolean> => {
  if (targetBaseline === null) return false;   // 无法确认 → fail-closed
  ...                                          // 比的是 targetBaseline
};
// 第 4 步的 lstat（本来就有）顺手把实际身份记下来
if (targetBaseline === null) targetBaseline = observed;
```

- 用户显式选过目标 → 基准是**他确认过的那一个**（变了必须拒绝，`ERR_ENTRY_TARGET_CHANGED`）；
- 没有预期（改名 / 项目根）→ 基准是**第 4 步本次读到的 lstat 身份**；
- `null` 一律视为"无法确认"，不再有"恒真"的分支。

四个使用点全部走同一个基准：**初次占位前**、10b 重新占位前、`rejectSourceChanged`
收敛、10d 最终核验，以及 `rename` 抛错后的清理分支（`verify()` 之外的最后一道）。

#### 拒绝码：同一件事实，两种可执行动作

| 场景 | 目录变了、占位未建立时 | 为什么 |
|---|---|---|
| 移动（用户显式选过目标） | `ERR_ENTRY_TARGET_CHANGED` | 用户要重新选目标 |
| 原地改名 / 项目根 | `ERR_ENTRY_SOURCE_CHANGED` | 目标父目录就是源所在目录；这一行已不在原位，该刷新的是源那一行 |

两者都是 409、都是"零副作用可证明"的明确拒绝。已经建立占位之后仍然一律 `UNKNOWN`
（§一的分叉不变），只是现在**改名也走这条分叉**了。

#### 不新增的东西

不扫描项目找占位、不删除任何非 `owned` 对象、不回滚、不自动重试、不加 HTTP 字段、
不动 `bigint`、不宣称消除 OS 级 TOCTOU。

### P02：真实加载结果的完整传递

#### 缺陷

```ts
// StructureRefreshHost（补丁前）
load(projectId: string, dir: string): Promise<unknown>;
// DocumentActionsContext（补丁前）
load: async (projectId, dir) => { await treeLoader.current.load(projectId, dir, false); },
```

`treeLoader.load()` 明明返回 `TreeLoadOutcome`（`applied` / `changed` / `rejected` /
`failed` / `stale` / `skipped-mode` / `skipped-inflight` / `skipped-no-cursor`），
被 `await` 之后**当场丢掉**。于是 `checkStructureLocationsWithOwnership` 只要没抛异常
就返回 `'applied'`，`structureUnknownNotice('applied')` 便理直气壮地说
"已只读刷新源位置与目标位置"——即使底层一次都没加载成功。

F03 修的是"提示要区分三种结局"，P02 修的是"结局本身是假的"。

#### 修正

1. `StructureRefreshHost.load` 的类型改为 `Promise<TreeLoadOutcome>`，实现直接
   `return treeLoader.current.load(...)`（不吞返回值）；
2. `checkStructureLocationsWithOwnership` 逐个收集真实结果，用
   `structureLoadVerdict(outcomes, worldChanged)` 合并成四种结论；
3. `refreshStructureSourceParent` / `refreshStructureTargetParent` 也走同一个合并函数
   （单层版本），不再"没抛异常就算成功"；
4. `structure-change.ts` 的 `runReadOnlyCheck` 原样透传结论，不再把 `partial` /
   `failed` 压成 `applied`。

| 结论 | 判据 | 文案 |
|---|---|---|
| `applied` | 每个必要位置都明确 `applied`，且世界没变 | 已只读刷新源位置与目标位置 |
| `partial` | 请求发出去了，但有位置没确认加载完成 / 世界在途中变了 | 只读刷新只完成了一部分 |
| `stale` | 零请求（闸门先作废） | 没有执行只读核对 |
| `failed` | 请求都发了，没有一个成功（含抛错） | 只读核对没有完成 |

仍然：不重发结构变更、Host 的 `UNKNOWN` 语义不变、核对失败也只报一次。

#### 目标重新确认的"新鲜度"

`ERR_ENTRY_TARGET_CHANGED` 之后要重取**目标所属父层**（§二）。重取会失败，失败时
层表里仍是旧锚。若把旧锚当"磁盘当前身份"交给"重新确认目标"，用户会拿着同一个过期锚
再撞一次，而且界面这次还说"已重新确认"。

对话框因此多记一个 `targetRefresh`（`idle` / `pending` / `done` / `failed`），
放行条件抽成纯函数 `moveTargetReconfirmProblem`：

| `targetRefresh` | 层表里的锚 | 放行 | 理由 |
|---|---|---|---|
| `done` | 任意 | ✅ | 本次重取明确成功 |
| `failed` / `pending` | 与冻结锚**不同** | ✅ | 用户手工刷新过，锚确实换了 |
| `failed` / `pending` | 与冻结锚**相同** | ❌ `MOVE_TARGET_UNREFRESHED` | 还是旧锚，不能说"已是最新身份" |

目标文件夹重新确认仍只由用户点击触发：不自动换锚、不自动提交、不自动重发。

### 本节新增不变量

8. 目录连续性的基准**不能只来自调用方**：没有预期时必须用本次执行读到的实际身份。
9. 底层加载的返回值必须逐层上传；`applied` 是唯一可以宣称"已刷新"的结论。
10. 旧缓存锚只有在"本次重取成功"或"锚确实变了"之后，才允许被当作最新身份确认。
