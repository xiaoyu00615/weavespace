## 一、F01：占位残留的结果语义（最高优先级）

### 缺陷

Provider 建立排他占位（0 字节文件）之后，如果目标父目录被外部**整体移走**并
在同路径建了新目录，旧实现的判定链是：

1. 10d `targetDirStillMatches()` = false；
2. `rejectSourceChanged('ERR_ENTRY_TARGET_CHANGED')`；
3. 内部 `reservationState()` 读的是**新目录里的同名路径** → `missing`；
4. 结论 `REJECTED`（"零副作用，可以放心重试"）。

但真实磁盘上，占位 `archive/a.md` 正躺在 `archive-old/` 里（F-08 的实测事实）。
**REJECTED 在这里是假的**：它声称没有留下任何副作用，而我们的占位还在用户的目录里。

### 修正

结果语义按"占位是否已经建立"分叉：

| 情形 | 结论 | 理由 |
|---|---|---|
| 未建立占位，目标目录身份已变（`ERR_ENTRY_TARGET_CHANGED`） | `REJECTED` | 零副作用可证明，用户可以重选目标重试 |
| 已建立占位，目标目录身份已变（10b / 10d / 源终检任一路径） | `UNKNOWN` | 占位跟着目录走了，去向与收敛都不可证明 |
| 已建立占位，目录连续、占位仍是 `owned` | `REJECTED` + 清理占位 | 可证明零副作用（先 `unlink` 再返回） |
| 已建立占位，目录连续但占位被外部换成 `foreign` | `UNKNOWN` | 绝不删外部对象，也无法证明收敛 |

配套三条纪律：

1. **从不扫描项目去找占位**。占位可能在任何一个被移走的目录里，挨个找等于遍历用户磁盘；
2. **从不删除移动后目录中的对象**。那是用户的目录，不是回收区；
3. **目标目录身份变化后，禁止在新同名目录中重新建立占位**。10b 与 10d 的重新占位
   分支都先认目录，再认占位——顺序反了就会在用户从未确认过的目录里留下痕迹。

### 代码落点

- `packages/storage/local-provider.ts`
  - 10b：`if (!(await targetDirStillMatches())) return unknown();` 位于 `reservationState()` **之前**；
  - `rejectSourceChanged()`：占位已建立时先核目录连续性，不成立直接 `unknown()`；
  - 10d：`return reserved ? unknown() : reject('ERR_ENTRY_TARGET_CHANGED')`；
  - 10d 的重新占位分支因此只会在"目录已核验"之后执行。

## 二、F02：目标身份变化后的恢复

### 缺陷

`ERR_ENTRY_TARGET_CHANGED` 只被显示成一条错误：层表里那个文件夹行仍挂着**过期锚**，
对话框也仍握着**冻结的旧锚**。用户唯一出路是关掉对话框重开——而重开并不保证他会做，
也不保证重开后读到的是新身份。

### 修正

1. **按世界票据重取"目标所属父层"**：`refreshStructureTargetParent`。
   - 目标 `archive` → 重取根层（锚在根层 `anchors['archive']`）；
   - 目标 `a/b` → 重取 `a` 层；
   - 目标 `''`（项目根）→ 重取根层（根锚是 `projectAnchor`）；
   - 跨工作区/跨代次 → 闸门作废，**零请求**。
2. **不自动替换冻结锚**：只把对话框标记为 `targetStale`（"目标身份已过期"）。
3. **显式入口**：对话框出现「重新确认目标」按钮；点击才重新捕获身份并清掉标记。
   重新选同一个路径不会触发 `<select>` 的 change，所以这个入口是必需的。
4. **重新确认前不得自动提交**：过期状态下按 Enter / 点确认，本地挡住并提示
   "请先点「重新确认目标」再提交"，零请求。
5. **不重发已拒绝的请求**：拒绝就是终止，恢复只能由用户的下一次明确操作触发。

### 真实浏览器证据

`browser-verification.json`：打开 → 选 `docs` → 外部删除重建 `docs` → 提交被拒
（`目标文件夹已被外部替换，未执行任何移动（请重新选择目标）`）→ 父层被重取 →
出现「重新确认目标」→ 过期状态下按 Enter 不发请求 → 点重新确认 → Enter 提交成功。
两次请求的 `targetAnchor` 分别是 `f43fb961…` 与 `057689b3…`（不同），
第一次请求源文件 inode / SHA-256 不变、目标未创建，全程只有 2 次 move 请求。

## 三、F03：UNKNOWN 提示的真实性 + 会话写入守卫

### 提示

旧文案无条件写"已只读刷新源位置与目标位置"。而只读核对有三种真实结局：

| `checkLocations` 结论 | 提示 |
|---|---|
| `applied` | 已只读刷新源位置与目标位置，请人工核对（不会自动重试、不会自行回滚） |
| `stale`（世界已换，闸门挡下） | 当前界面已经切换，**没有执行**只读核对，请手动刷新后核对 |
| `failed`（抛错/未完成） | 只读核对**没有完成**，请手动刷新后核对 |

三种都不承诺自动重试；核对失败**不会**触发结构变更重发。Host 的 `UNKNOWN`
语义原样保留（`status` 仍是 `UNKNOWN`，不因提示文案改变判定）。

### 会话写入守卫

结果回来时，界面可能已经换了会话（对话框被关闭又对另一行重开）。旧实现先用 ref
读一次"还是不是我"，再 `setState(null)` / `setState({...submitting:false})`：
两次读之间新会话可能已经挂上，旧结果会改写**新会话**的错误位、提交状态，
甚至把它关掉。

现在三种写回（写错误 / 改提交状态 / 收起会话）都经过
`updateSessionIfOwned(current, sessionId, sessionIdOf, update)`：

- `current === null` → 不复活；
- 票据不符 → 原样返回（一个字段都不改）；
- 票据相符 → 才执行更新（`update` 返回 `null` 时才收起）。

不建立第二套会话框架：票据仍是 `StructureIntent.sessionId`，判据仍是
`structureSessionApplies`。

## 四、不变量（在 R2.1 之上新增/收紧）

1. 占位一旦建立，"零副作用"就不再是可以随口宣称的结论：证明不了 → `UNKNOWN`。
2. 结果语义按"占位是否已建立"分叉，不按"当前路径上有没有同名文件"推断。
3. 重新占位前必须核验目标父目录身份；目录变了就不许在新目录里留下任何东西。
4. 目标身份被拒 → 重取目标所属父层（按世界票据）；跨世界零请求。
5. 恢复只能由用户显式动作触发：不自动换锚、不自动提交、不自动重发。
6. `UNKNOWN` 的提示必须与实际核对结局一致。
7. 结果只能写进发起它的那个会话；票据核验在函数式更新器内部完成。
