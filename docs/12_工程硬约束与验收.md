# 硬约束与规范（F0 提案，建议签收后作为工程门槛）

## A. 架构硬约束

- **ARCH-001** Core 没有具体文件格式分支；格式功能通过公开 Capability / 插件注册。
- **ARCH-002** 客户端不能访问 Host 的私有 DB、密钥或特权文件 API。
- **ARCH-003** 权威数据所有者唯一；Derived 不得覆盖 Authored；业务状态不能靠调试日志恢复。
- **ARCH-004** 文件插件、存储插件、AI 适配器、网络入口必须分层，不重复编辑/保存引擎。
- **ARCH-005** 任何新功能先查模块目录，不随意新建责任重叠的服务。

## B. 开发与目录硬约束

- **ENG-001** 每个独立功能拥有模块/目录与单一公开入口；跨模块只使用契约。
- **ENG-002** 严禁“巨型公共文件”或跨模块 import 内部源码；自动 CI 检查依赖边界、循环依赖。
- **ENG-003** 新增公共契约需要版本、迁移/兼容计划、ADR 和契约测试。
- **ENG-004** 配置分 global/device/project/user/plugin，不把本机路径、秘密同步为仓库配置。
- **ENG-005** 新模块附最小 README：职责、公开 API、数据所有权、失败路径、测试入口。

## C. 可观测性与时间硬约束

- **TIME-001** 正式日志、审计、状态变化必有 UTC ISO 8601 时间戳。
- **TIME-002** 修改/保存/错误/重试/完成必须是明确不同事件，记录 traceId/operationId 与结果。
- **TIME-003** 事件顺序使用特定流 sequence/version，不以多设备墙钟确定因果。
- **OBS-001** 故障可按模块、资源、时间、traceId 追踪；日志有轮转与敏感数据脱敏。
- **OBS-002** 关键模块有独立健康状态、错误码和诊断；插件故障原因可由 Core 读取。

## D. 数据、安全与写入硬约束

- **DATA-001** 原始文件默认只读；写入必须由具备授权的命令触发，版本检查及结果确认。
- **DATA-002** dirty 状态绝不能在无确认时被卸载/关闭静默丢弃。
- **DATA-003** 多文件操作失败可以部分提交时，必须显式 PARTIAL/UNKNOWN 并提供修复，不伪称整体原子回滚。
- **SEC-001** 默认 localhost、默认关闭 LAN；每一次资源请求都校验身份和授权。
- **SEC-002** 密钥不得进入源库/日志；文件正文视为不可信内容；插件申请权限不等于获得权限。
- **SEC-003** 不明来源插件与不可信解析文件必须有隔离策略；若首版未实现强隔离，应限制信任范围并写明限制。
- **NET-001** 远程设备经 Host API，不能通过共享目录直接并发写 SQLite。
- **AI-001** AI 读作用域与写权限分开；模型回答不等于实际保存；高风险修改需要预览/审批。

## E. 测试门槛

- **TEST-001** 正常与失败路径同样有自动测试；失败注入至少覆盖保存冲突、磁盘错误、插件异常、重复命令、未授权访问。
- **TEST-002** 新增一类插件时不能修改已有业务模块源代码，允许只在注册配置/契约扩展处产生变动。
- **TEST-003** 每阶段报告 Git Commit、系统版本、测试清单、PASS/FAIL/BLOCKED 与最小故障日志，不用无限新增取证包。

## 设计原则与实现事实不可混淆

硬约束“应该如此”不等于代码已经做到。只有相应测试通过，才允许将该能力从 PLAN 改为 IMPLEMENTED/VERIFIED。架构不承诺零重构，但公共边界稳定、模块内部可换实现。
