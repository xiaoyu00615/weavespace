# UX-02C-04 资源元数据契约（标注名 / 标签 / 行颜色）

状态：**实施稿**（本轮实现与其提交见交付报告；本文件与代码同步维护）
范围：WeaveSpace 工作台展示元数据，不含搜索、筛选中心、批量标注、自定义文档格式。

---

## 一、现有架构调查（实施前实测）

写这份契约之前逐项读了源码，以下结论都有出处，不是假设：

| 关注点 | 现状 | 对本阶段的影响 |
|---|---|---|
| 工作区配置 | `apps/server/src/store/config.ts`，v4（`commitSeq/issuedIds/revoked/projects/hidden/trash`），checksum 是"按文件声明版本"的 canonical JSON SHA-256 | 元数据必须进这份配置并升到 v5，且 v2/v3/v4 必须继续可复算 |
| 配置提交 | `store/file-store.ts`：每次变更构造完整 `ConfigState` → `writeConfigAtomic` → `applyConfig`（同步，内存投影与磁盘同一步） | 元数据写入沿用同一提交点，不新建文件、不新建服务 |
| 资源身份 | `StorageProvider.identityOf(path)` 返回 `dev:ino`；隐藏记录已用 `projectId + path + rootToken + identity` 四元组 | 元数据复用**同一套**身份，不再造第二套 |
| 隐藏记录 | `hidden.ts` + `ConfigHiddenEntry`：读取时逐条核验 `active/missing/rebound/unverified` | 元数据读取侧同构（同四种状态），语义差异见 §5.4 |
| 文件树 | `/api/tree` 逐层分页，`TreeEntryDto{id,name,kind,extension,relPath,hidden,hiddenBy}`，快照 SHA-256 覆盖整层集合 | 元数据作为 `meta` 挂在 DTO 上；**不参与**快照（见 §6.3） |
| 结构变更 | `structure-change.ts`：屏障 → 会话保护 → `moveEntry`，结果 `APPLIED/REJECTED/UNKNOWN` | 迁移只在 `APPLIED` 后做，失败不回滚（§7.2） |
| 回收区 | `ConfigTrashEntry` 带 `identity`，恢复时三方核对（原路径/大小/身份） | 回收**不需要**任何新钩子：记录靠身份自动失效/复原（§8） |
| 插件能力 | `capabilities/` 按扩展名解析查看器，与树/元数据无耦合 | 新格式（`.wnote` 等）天然复用元数据，不需要改核心 |
| Shell 状态 | `treeByProject` 层表 + `tree-model.ts` 纯函数 + `DocumentActionsContext` 编排 | 元数据走 `entryToNode`/`applyPage` 一条直线，不新增第二份状态 |

**结论**：现有配置/身份/事务机制足够承载元数据，**不需要**新数据库、第三套浏览器持久化或重复的身份体系。

## 二、权威存储位置

唯一权威：**工作区配置文件的 `metadata` 数组**（v5）。

```
<workspace-store>/workspace.json
{
  "version": 5,
  "commitSeq": 42,
  "issuedIds": [...],
  "revoked": [...],
  "projects": [...],      // v2
  "hidden": [...],        // v3 起
  "trash": [...],         // v4 起
  "metadata": [...],      // v5 起（本阶段）
  "checksum": "..."
}
```

明确禁止（已实现为"结构上做不到"）：

- 不写用户文件正文、不改扩展名、不改文件名；
- 不在用户目录里创建任何配置文件（一切都在 WeaveSpace 自己的 store 目录）；
- 不用 localStorage / IndexedDB 存元数据（那里只有回收区的**待核对台账**，与展示元数据无关）；
- 不做"只存在 React state"的临时标注：刷新/重启后必须还在。

`checksum` 覆盖 `metadata`：手工改一个标注名而不更新校验和 → 整份配置判损坏（fail-closed）。

## 三、数据结构

```ts
interface ConfigMetadataEntry {
  projectId: string;              // 作用域
  path: string;                   // 项目内相对路径；'' = 项目根展示项
  rootToken: string;              // 项目根身份（换根即失效）
  identity: string;               // 对象身份 dev:ino；根为根令牌本身
  alias?: string;                 // 标注名（规范化后 1..80，无控制字符）
  tags: string[];                 // 0..16，每项 1..24，大小写不敏感去重
  color?: ResourceColor;          // 'red'|'orange'|'yellow'|'green'|'blue'|'purple'|'gray'
  updatedAt: string;              // 诊断用，不参与判定
}
```

约束（解析期强校验，任一条不符即判配置损坏）：

- `(projectId, path, rootToken, identity)` 唯一（路径按平台大小写口径比较）：
  **同一路径允许存在多条记录**（不同对象先后住过这个位置），但同一个对象
  不可能同时有两条标注；
- `alias` 必须已 trim、非空、≤80、无控制字符；
- `tags` 必须已 trim、非空去重（大小写不敏感）、每项 ≤24、总数 ≤16；
- `color` 必须在 token 表内；
- **三个展示字段至少有一个**：全空的记录没有意义，出现即损坏
  （"没有标注"只有一种表示：整条记录不存在）。

上限 `MAX_METADATA_ENTRIES = 2000`（配置体量护栏，写入口 `ERR_METADATA_LIMIT` 明确拒绝，
**不静默淘汰**用户写过的标注）。

### 3.1 唯一性是身份四元组，不是"项目 + 路径"（R1-01）

用户会遇到的真实情形：`a.md` 被回收（或外部删除），原位置又放了一个**同名的另一个文件**。
两者是不同对象，各自可能都被标注过。因此：

- 记录按 `(projectId, path, rootToken, identity)` 唯一，同一路径可以有多条；
- 读取侧只取 `identity` 与当前对象**完全一致**的那条（§5.4），其余如实报告
  `missing` / `rebound`，绝不套到新对象上；
- 增量写入只在四元组完全一致时合并——路径相同但对象换了，旧记录与本次写入无关：
  既不拿它的字段补齐（那会让新文件继承旧标注），也不覆盖它（那会静默销毁旧对象的历史，
  恢复后标注就没了）；
- 清除当前对象只删**那一条**；同路径上别的对象的历史记录必须留着
  （`scope: 'object'` 与 `scope: 'stale'` 的区别，见 §4.2）。

### 3.2 为什么是"身份四元组"而不是文件名

同名文件在两个项目、同一项目两个目录里都是**不同对象**。用路径当身份会导致：

- A 的 `README.md` 标注出现在 B 的同名文件上；
- 文件被外部删除后新放一个同名文件，继承了旧标注（用户会以为"这是我标的那个"）。

因此每条记录都存 `rootToken + identity`，读取时按当前磁盘事实核验（§5.4）。
`path` 只是**定位器**，它可以随真实改名/移动被重写（§7），身份不变。

## 四、API

三个端点，全部要求 T1 会话令牌；两个写端点额外要求显式同源 `Origin`。

### 4.1 `POST /api/metadata/set`

```json
{ "projectId": "proj-a", "path": "docs/a.md",
  "alias": "核心架构", "tags": ["重要","架构"], "color": "blue",
  "anchor": "0f3c…（32 位十六进制，可选）" }
```

**增量语义**（三态，每个字段独立）：

| 字段 | 缺省（不传） | `null` / `[]` | 有值 |
|---|---|---|---|
| `alias` | 保持原值 | 清除 | 设置为该值（trim 后为空等同清除） |
| `tags` | 保持原值 | 清空 | 整体替换（规范化） |
| `color` | 保持原值 | 清除 | 设置为该 token |
| `anchor` | 不声明身份预期 | 同缺省 | 与 Host 自己核验的身份比对（§4.5） |

为什么必须增量：两个窗口同时看同一个文件，A 改颜色、B 改标签。若每次提交全量，
后保存的会把对方刚写的值覆盖回自己屏幕上的旧值。

响应：`{ status:'APPLIED', projectId, path, changed, metadata:{alias?,tags,color?} }`；
`changed:false` = 内容没变化（幂等，不写盘、不推进 `commitSeq`）。

校验顺序（与实际实现一致）：模式 501 → T1 403 → Origin 403 → 体/路径/锚形状 400（零 IO）
→ 项目可用性 503/404 → 项目级写授权 403 → 内部保留路径 403 → 身份核验（`withDiskOp`）
→ **资源锚比对**（不一致即 409，零写入）→ 配置原子提交。

失败语义：

- 目标不存在 → 404 `ERR_RESOURCE_NOT_FOUND`（不登记"看不见的标注"）；
- Provider 无身份能力 → 501 `ERR_COMMAND_UNSUPPORTED`；
- 配置写不进去 → `ERR_PERSIST_FAILED`，内存投影不变（绝不"接口说成功、重启就没了"）；
- 超上限 → 409 `ERR_METADATA_LIMIT`；
- 携带的锚与当前对象不符（对象被替换、或已不存在）→ 409 `ERR_METADATA_TARGET_CHANGED`，
  **零写入**。这不是"保存失败"，而是"这次编辑已经不再指向那个对象"（§8.1）。

### 4.2 `POST /api/metadata/clear`

```json
{ "projectId": "proj-a", "path": "docs/a.md",
  "anchor": "…（可选）", "scope": "object | stale（可选）" }
```

三种情形必须分清，绝不能用一句"清除"糊过去：

| 请求 | 语义 | 对象已被替换/已消失 |
|---|---|---|
| 带 `anchor`（`scope` 缺省 `object`） | 只删**那个对象**那一条 | 409 `ERR_METADATA_TARGET_CHANGED`，零删除 |
| 不带 `anchor`，对象存在 | 删当前对象那一条（旧客户端等价语义） | — |
| `scope: 'stale'` | 只删**身份对不上**的记录，当前对象的记录保留 | 该路径上的记录全部按失效清理 |

对话框的"清除"永远走第一条：它绝不能顺手删掉同路径别人的历史记录。
"清理失效记录"是**另一个动作**（`scope: 'stale'` 或不带锚且对象已不存在），
响应里如实回报 `scope: 'object' | 'stale'`，界面文案也必须不同。

### 4.3 `GET /api/metadata?projectId=`

只读；返回每条记录的 `{ path, state, alias?, tags, color? }`。
`state ∈ active|missing|rebound|unverified` 是**核验结论**，不是新状态机。

### 4.4 树端点携带

```ts
// 每个条目
meta?: { alias?: string; tags: string[]; color?: string }
// 每页顶层
projectMeta?: { alias?: string; tags: string[]; color?: string }   // 只在 level === ''
anchors?: Record<string, string>                                   // relPath → 资源锚
projectAnchor?: string                                             // 只在 level === ''
```

只有 `active` 的记录会出现在这里 —— **客户端不做任何"是不是同一个文件"的判断**。

**锚为什么不放进条目**：条目描述"这一层有哪些东西"，锚描述"那一行此刻是哪个对象"。
保存文件是"临时文件 + rename"，**必然换 inode**，锚因此每次保存都会变；若把它塞进条目，
任何一次普通保存都会改变"条目集合"，于是"别的操作不该影响这棵树"这类比较会变成假失败。
锚表按页合并（第一页替换、续页叠加），续页不带某条目的锚时不会抹掉它上一页的值。

### 4.5 资源锚（编辑会话的身份预期）

```text
anchor = SHA-256("ws-meta-anchor-v1\n" + projectId + "\n" + pathKey(path) + "\n" + rootToken + "\n" + identity)
         取前 32 位十六进制
```

（用换行做分隔符而不是直接拼串，是为了让 `ts` / `t` 这类前缀巧合不会算出同一个锚；
`pathKey` 是平台大小写口径的路径键，与记录唯一性用的是同一个函数。）

- 它是**不透明**的：客户端不解析、不据此授权，也推不出 `dev:ino`；
- 它**不是身份**：客户端提交的身份自述字段（`identity` / `rootToken` / `rootPath` …）
  一律 400 拒绝；
- 它**不是授权**：写入仍然走项目级授权判定，身份仍然由 Host 自己 `lstat`；
- 它只有一条用途：Host 用自己刚核验出的身份**重算一遍**，与请求里的锚比对。
  一致 → 这次编辑仍指向那个对象；不一致 → 409，零写入。

### 4.6 发送前的最终裁决（R1-H1-01）

编排层在"用户按下保存"时判过一次归属，但传输层还要 `await sessionToken()`。
这段窗口里用户完全可以切工作区、切项目，或者让文件被替换——早先那次判定已经通过，
POST 会照发。所以最后一次判定必须压到 **`sessionToken()` 返回之后、`fetch()` 之前**：

```ts
postMetadata(endpoint, payload, gate)   // gate 必填
  token = await sessionToken()
  // ↓↓↓ 从这里到 request() 之间不允许出现任何 await ↓↓↓
  decision = evaluateMetadataSendGate(gate)
  if (!decision.ok) return { status: 'NOT_SENT', reason }
  response = await request(...)          // request() 的第一句就是 fetch()
```

- `gate` 由**编排层**提供（`metadata-session.ts` 的 `sendGateOf`），判据与提交前那次
  完全相同（工作区身份键 + 项目 + 路径 + 资源锚），只是时刻不同；
- 设置与清除**两条**路径都走同一段代码（`postMetadata`），不存在"只保护了保存"的缝；
- 结果是 `NOT_SENT`，**不是** `UNKNOWN`：`UNKNOWN` 表示"发出去了但没结论"，处理方式是
  刷新核对；这里连服务端都没碰，刷新只会读到一份与本次编辑无关的旧状态，还会让用户
  以为"可能写进去了"；
- 拒绝之后零 POST、零刷新、零副作用；同一工作区内明确提示"没有保存"，
  工作区已经切走则**静默丢弃**（提示不能落到别人的工作区里）；
- `gate` 漏传 / 抛异常 / 返回无法识别的形状 → 一律按拒绝处理（fail-closed，
  原因 `target-unverified`），绝不"假装检查过"；
- 它**不替代** Host 的资源锚核验：客户端能提供的仍然只是"当时看到的那一行"，
  权威身份始终由 Host 自己 `lstat` 得出。

## 五、语义

### 5.1 标注名

- 附加展示信息，**不替代**真实名称：行上显示 `architecture.md（核心架构）`；
- 不改文件名、不改内容、不改扩展名、不影响插件识别与打开/保存/移动/回收；
- 可清除，清除后恢复只显示真实名称。

### 5.2 标签

- 一个资源多标签；添加/移除；trim 去空；按**大小写不敏感**去重（保留首次写法）；
- 不允许空标签；上限 16 个、每个 24 字符；
- 不改动其它资源上的同名标签（没有全局标签表，本阶段不做管理中心）；
- 数据结构天然支持将来的搜索/筛选：`projectId + path + identity + tags` 足以建立倒排索引，
  且不依赖任何 UI 状态。

### 5.3 行颜色

- 只存**语义 token**，不存 `#rrggbb` 或任意 CSS 字符串；
- token → 色值的映射只有一处（`styles/shell.css` 的 `.tree__row--color-*`）；
- 颜色只作用在**文件名**上，且排除选中行：不覆盖选中/焦点/禁用/错误状态。

### 5.4 读取侧核验（四种状态）

| 状态 | 含义 | 是否展示 |
|---|---|---|
| `active` | 路径上仍是当初那个对象 | ✅ |
| `missing` | 路径上已没有对象（删除/移走/在回收区） | ❌ |
| `rebound` | 路径上换成了另一个对象 | ❌（记录保留，但绝不套到新文件上） |
| `unverified` | 无法核验（无身份能力 / IO 异常） | ❌ |

与隐藏记录的差别：隐藏遇 `unverified` **继续隐藏**，元数据遇 `unverified` **不显示**。
两者是同一条原则的两面——拿不准的时候不要声称一件用户没有确认过的事实
（隐藏是"别暴露"，标注是"别乱贴"）。

## 六、UI 展示规则

1. 行文本 = `真实名称` +（可选）`（标注名）` +（可选）标签胶囊；
   - **没有标注名**时：最多 2 枚标签胶囊 + `+N`；
   - **有标注名**时：标签折成一枚 `+N`（内容进 `title`）。
     侧栏只有 260px，"名称 + 标注名 + 两枚标签"放不下；真实名称与标注名是用户
     正在确认的信息，标签让位（对话框里完整可编辑，`title` 里全列）。
2. 行颜色只改文件名颜色，选中行不受影响；
3. 右键菜单三个入口：`设置标注名…` / `编辑标签…` / `设置颜色…`，打开同一个对话框并把焦点放到对应分区；
4. 对话框支持逐项清除与"清除全部标注"；失败**不关闭**（用户输入还在），`UNKNOWN` 关闭并提示"未确认"；
5. 保存后只重取**该路径所在的那一层**（项目根标注重取根层），不动标签页、草稿、展开状态、选中项；
6. 链接节点没有入口（Host 同样拒绝）；未授权/演示模式给出禁用与原因；
7. 项目根行的标注来自根层 `projectMeta`，用项目身份关联，不获得任何根目录操作权限。

### 6.1 元数据不参与目录快照

`directorySnapshotOf` 只覆盖 `kind/name/relPath/extension/hidden/hiddenBy`。
元数据不改变"这一层有哪些条目"，因此改一个颜色**不该**让正在进行的翻页作废
（否则用户在大目录里翻到第 3 页时保存一次标注就会被打回第一页）。

## 七、真实资源生命周期

### 7.1 回收与恢复（无需新钩子）

- 回收只改 `trash`，**不动** `metadata`；文件离开原路径后核验结果是 `missing`，
  因此树里不显示；
- 同名新文件落到同一路径时，它是**另一个身份**：核验旧记录得 `rebound`，核验新记录
  （若用户给它设过标注）得 `active`。两条记录同时存在于配置里（唯一性是四元组，
  见 §3.1），互不覆盖——这既是"新文件不继承旧标注"，也是"旧文件的标注不会因为
  新文件出现就被悄悄删掉"；
- 恢复把**同一个对象**放回原路径 → 旧记录重新 `active` → 标注自动生效；此时若同名
  新文件已经被移走，它那条记录变 `missing`，同样保留；
- 恢复冲突（目标已被占用而失败）不会改动任何元数据记录。

为什么"发现 `rebound` 就删"是错的：删除不可逆，而"文件只是暂时不在这个路径上"是常态
（回收区、外部工具搬走、网络盘掉线）。判据是**身份**而不是路径，因此留一条 `rebound`
记录永远不会污染当前路径上的对象。清理只发生在用户显式要求时（`scope: 'stale'`，见 §4.2）。

这条设计是刻意的：回收区已经有完整的事务状态机与身份证据，**再加一个元数据接入点
只会制造第二个"什么算同一个文件"的判定**。

### 7.2 真实改名 / 移动（R1-02：只迁移真正移动的对象）

迁移的输入**不是**"旧前缀 + 新前缀"，而是调用方逐条核验身份后给出的移动清单：

```ts
commitMetadataRelocate({
  projectId,
  rootToken,
  moves: [{ from, to, identity }],   // "这个身份从 from 搬到 to"
})
```

类型上就不存在"按路径前缀猜"这条路——猜错的代价是把 A 的标注贴到 B 上，而且是
在用户看不见的地方完成的。

单个路径的判定顺序：

| 磁盘事务结论 | 是否迁移 | 说明 |
|---|---|---|
| `APPLIED` 且 `identityOf(to) === 记录.identity` | ✅ 只改 `path` | 唯一允许迁移的情形 |
| `APPLIED` 但目标身份不符 | ❌ 留原位 | 变 `missing` / `rebound`，不套到新对象 |
| `APPLIED` 但目标读不到（IO 异常） | ❌ 留原位 | 变 `unverified`，不猜 |
| `REJECTED` / `not-committed` | ❌ 一点不动 | 磁盘没变，迁移会凭空造出错误路径 |
| `UNKNOWN` / 无法判定 | ❌ 不迁移 | 连对象在哪都不知道 |

补充约束：

- 目录移动时对**每个后代单独核验**，不整批信任目录级证据，也不使用前缀展开；
- `rootToken` 必须与原记录一致；换过目录 / 重新授权后令牌变化的记录不参与迁移；
- **去重键是完整四元组 `projectId + rootToken + path + identity`**（R1-H1-02）。
  只按 `path + identity` 会跨项目/跨根令牌误伤：同一个对象完全可能同时出现在两个项目里
  （硬链接、嵌套授权），那时另一个项目的记录会被当成"重复"，把本次真实迁移的记录静默
  丢掉——配置里看不出异常，用户只是发现标注没了。路径按平台大小写口径归一
  （Windows 下与 `sameEntryPath` 同一规则）；
- 目标路径上已有的记录：同一**四元组** → 只留一条（`kept`/`deduped` 分开统计）；
  不同身份、别的项目、别的根令牌 → 那是另一个对象或另一份授权下的历史，
  **不覆盖、不删除**，各自并存；
- 迁移写配置失败**不改变** HTTP 结果：磁盘确实已经变了，此时报错会诱导用户重试一次
  真实移动。响应里显式给 `metadataMigration: 'moved'|'none'|'failed'` 与 `metadataMoved`
  计数，Shell 用独立文案说明"文件已移动，但资源标注未能随文件迁移"，绝不显示成
  磁盘操作失败。客户端对这两个字段做**严格窄化**（只认三个字面量与正整数），
  形状不对一律当成"没有迁移信息"而不是"迁移成功"。

### 7.3 项目根与项目撤销

- 根记录 `path === ''`、`identity === rootToken`（根没有 `dev:ino` 意义上的对象身份，
  根令牌就是它的身份）；根令牌变化（重新授权 / 换目录）→ 记录不再 `active`；
- 根记录的锚是 `SHA-256` 里参与演算的 `pathKey('')`，因此根层的 `projectAnchor`
  同样不可伪造（见 §4.5）；
- **项目被撤销后，元数据记录在配置里保留**（`metadata: current.metadata` 原样写回），
  与回收记录同向；这与隐藏记录**不同**（隐藏会被过滤掉）。原因：撤销不删除任何磁盘
  文件，配置里多留一条不可见的记录不构成任何可见性、权限或容量风险，而"删掉就再也
  找不回来"是不可逆的；
- 不可见性由读取侧保证：`metadataOf(projectId)` 对**非现存项目**恒定返回 `[]`，
  因此"墓碑已生效、配置尚未补写"的中间态不会漏出一条记录；重新添加同一目录会得到
  新的 `projectId`，旧记录永远不会被新项目命中；
- 撤销把 `mutationsAllowed` 收窄时，元数据写入与其它写入一样被拒绝（不产生半条记录）。

### 7.4 保存后的身份再绑定与四元组冲突（R1-01 / R1-H1-02）

保存是"临时文件 + rename"，**必然换 inode**；不刷新的话，用户标注一个文件、编辑并保存，
记录立刻变 `rebound`，标注从界面上消失——而文件其实还是同一个文件。因此
`COMMITTED` 之后会做一次 **update-only CAS**（`commitMetadataUpdateIdentity`）：

| 前置事实 | 结论 |
|---|---|
| 记录不存在 / 根不同 / 身份不是 `expectIdentity` | `skipped-missing`，零写入 |
| 目标身份与当前身份相同 | `unchanged` |
| **目标四元组已有另一条记录** | `skipped-conflict`，零写入 |
| 其余 | `updated`：只把这一条的 `identity` 换掉 |

`skipped-conflict` 的三种"不做"都是刻意的：

- **不写入**：写下去就是两条同一四元组的记录，而 `parseConfig` 把重复四元组判为损坏
  ——下次启动整份配置都读不出来，代价远大于"这次没刷新"；
- **不覆盖目标记录**：那是另一个身份的标注，静默改动它比不刷新更糟；
- **不删旧记录**：它仍是一条可能还有用的历史（用户可能还要恢复那个对象）；
- **不抛错**：调用方是**已经成功的正文保存**，这里失败绝不能反过来把保存说成失败。

代价是这条标注暂时停在旧身份上（读取侧如实报 `rebound`，界面不显示），用户可以重新设置。
这是"宁可少一个标注，也不写一份读不出来的配置"。

## 八、失败与 UNKNOWN

| 场景 | 结果 | 客户端行为 |
|---|---|---|
| 形状/上限/颜色非法 | 400 `ERR_COMMAND_INVALID` | 对话框保留输入并显示原因 |
| 目标不存在 | 404 `ERR_RESOURCE_NOT_FOUND` | 同上 |
| 保留路径（回收区内部命名空间） | 403 `ERR_PATH_RESERVED` | 同上（正常情况下 UI 不会给出这种入口） |
| 越界 / 未授权 | 400 / 403 | 同上 |
| 容量达上限（2000 条） | 409 `ERR_METADATA_LIMIT` | 提示先清理失效记录，**不自动淘汰** |
| 携带锚且与当前对象不符 | 409 `ERR_METADATA_TARGET_CHANGED` | 视为"对象已经换了"，按 stale 处理，**不当成普通失败** |
| 配置写入失败 | `ERR_PERSIST_FAILED` | 明确失败，不假装成功 |
| **发送前裁决不通过**（令牌在途时世界变了） | 无请求，`{ status:'NOT_SENT', reason }` | 按 stale 处理：同工作区提示"没有保存"，已切走则静默丢弃 |
| 网络中断 / 超时 | `{ status:'UNKNOWN' }` | 刷新该层核对真实结果；**不自动重发** |

`NOT_SENT` 与 `UNKNOWN` 的区别是这一节最容易被写错的地方：前者"服务端没见过这个请求"，
后者"服务端可能见过"。把前者当后者，用户会去核对一份与本次编辑无关的旧状态，
并倾向于"再点一次"；把后者当前者，则会把一次可能已经成功的写入说成"没发生"。

`UNKNOWN` 为什么安全：写入是幂等的（同一份内容重复写结果相同），且提交是"整份配置
原子落盘"，不存在半条记录。因此核对即可，不需要像回收区那样保留待核对台账。

### 8.1 stale 与 failed 必须分开

编辑会话的四类"这条标注不该落地了"各有独立文案（`metadataStaleNotice`）：

| 原因 | 触发 | 文案方向 |
|---|---|---|
| `workspace-switched` | 提交前后会话绑定（工作区身份 + 项目身份）变了 | "工作区已切换，这次标注没有保存" |
| `target-changed` | 锚不符 / 身份不符 → 409 | "目标资源已被替换，这次标注没有保存" |
| `target-missing` | 提交前目标已不在该路径 | "目标资源已不存在，这次标注没有保存" |
| `target-unverified` | 无法确认目标身份（无身份能力 / IO 异常） | "无法确认目标资源的身份，请刷新后重试" |

（`workspace-switched` 的判据是会话身份键 `模式 + 工作区模式 + 工作区摘要 + 加载代次`；
项目切换不需要单独一类——绑定里的 `projectId` 在新工作区的层表里查不到，天然判为
`target-missing`。少一个分支就少一种"两条文案说的是同一件事"的困惑。）

区分它们的意义：`failed` 意味着"可以原样重试"，`stale` 意味着"重试会写错对象"。
把后者显示成前者，用户会按提示再点一次保存，于是旧草稿落到新文件上——这正是 R1-03
要挡住的事。

## 九、配置版本升级

- v1–v4 **只读兼容**：加载时升级为 v5 内存视图，`metadata` 视为空；
  校验和按**文件声明的版本**复算，因此历史配置不会被判损坏；
- 任意一次写入（隐藏、回收、元数据、改名…）都以当前版本（v5）写回，
  旧字段（`hidden`/`trash`/`projects`/`revoked`）原样保留；
- v5 文件少了 `metadata` 数组或某条记录非法 → 整份配置不可用（fail-closed，
  与既有 v3/v4 的行为一致）；
- 校验和的排序键（`canonicalMetadata`）是 `projectId → path → identity → rootToken`。
  R1 之前每路径最多一条记录，"路径相同"就已经唯一；改成四元组唯一之后必须把
  `identity` 与 `rootToken` 也纳入排序，否则同路径多记录的顺序不确定，
  同一份内存状态会算出两种校验和；
- **既有 v5 配置零迁移**：旧文件里同一个 `(projectId, path)` 至多一条记录，
  新代码读它仍然只有一条，`canonicalMetadata` 的输出顺序与旧实现完全一致
  （单条记录时 `identity` 不参与比较）——因此升级后第一次启动不会报校验和不符，
  也不会触发任何重写；
- 去重判据同样是四元组：`(projectId, path, rootToken, identity)` 全等才算重复。
  同路径不同身份是**合法的**，不是损坏。

## 十二、已知能力边界

本节列出**明确没有解决**的问题。写成文档而不是留给读者推测，是因为"看起来解决了"
比"明知没解决"更危险。

### 12.1 `dev:ino` 能证明什么

对象身份来自 `stat` 的 `(dev, ino)`，因此它能证明：

- 同一路径上的**当前对象**是否仍是当初那个对象（换文件、改名覆盖、删除后重建）；
- 不同路径上的两个对象是否是同一个对象（硬链接会得到相同身份，这是对的）。

它**不能**证明：

- 文件内容没变（内容变化不改变 `dev:ino`；身份只回答"是不是同一个文件"，
  它在被原地覆盖时保持不变是正确的语义）；
- 记录里的身份对应的文件**还在**（inode 会被回收并复用）；
- 身份在两次 `stat` 之间一直有效。

### 12.2 操作系统层的身份复用与 TOCTOU

- **inode 复用**：文件删除后，同一 inode 号可能被新文件拿到。极端情况下新文件会
  得到与旧记录相同的 `(dev, ino)`，从而被判为 `active`。缓解手段只有"删除时同步清记录"
  与"记录里带 `updatedAt` 供人判断"，**本轮没有做也无法在此层做真正的防护**——
  要彻底解决需要一个不复用的标识（例如每文件一份 sidecar 标记），那会污染用户的目录；
- **TOCTOU**：核验身份与真正读写之间始终存在时间窗。本轮的做法是"核验点尽量贴近
  提交点"（锚在 POST 边界比对、迁移在 `withDiskOp` 内逐条核验），把窗口压到最小，
  但**不声称窗口为零**；
- **跨进程/跨设备**：别的程序在窗口内替换文件，本进程无从知晓。这不是本契约能解决的问题，
  也不是本阶段的目标。

### 12.3 由此产生的产品行为

正因为上面两条无法根除，失败方向被刻意定为"不显示"而不是"显示错的"：
`unverified` 不展示、`rebound` 不展示、锚不符一律 409。用户看到"标注没了"时，
真相通常是"那个文件确实不是原来那个了"。

## 十三、明确不做（本阶段）

全局搜索、标签筛选中心、批量标注、自定义知识文档、快速笔记、三维/画布/AI、
新主题系统、正式 UI 重构、目录回收/项目根删除/永久删除。

但契约已为它们留好位置：身份四元组（§3.1）足以做索引与迁移，
颜色是 token 而非色值，标签是规范化数组而非自由文本。
