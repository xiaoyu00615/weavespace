## 0. 结论摘要

三项与既有结论不同的发现，其中两项属于阻断级：

| 编号 | 结论 | 级别 | 依据 |
|---|---|---|---|
| D-1 | **新建文件会话在项目根被删除/移动后，保存会重建整个根目录并返回 COMMITTED** | 阻断 | 运行时复现（见 §1.3） |
| D-2 | `/api/document/disk` 使用全局单例 Provider，而不是会话绑定的 Provider | 阻断（多项目） | `apps/server/src/server.ts:356` |
| D-3 | `/api/health` 向浏览器返回 `rootDir` 绝对路径，且有测试在**强制**该行为 | 需裁决 | `server.ts:336`；`tests/suites/20-s9b-live-file.test.ts:127` |

补充结论：

- Session 直接持有 Provider 对象且**永不回收**（`document-service.ts:125`、`369-393`），这是 R1 全部风险的根因。
- `providerId` 在 `local-provider.ts:176` 硬编码为 `'local'`，多项目改造必须先把身份变成可注入参数，否则所有项目会被判定为"同一存储根"。
- 现有 `RootBoundary` 允许"根尚不存在"（`verified:false`），因此**不能**直接当作 Registry 的 READY 判定。

## 1. 当前代码事实

### 1.1 会话与 Provider 的绑定方式【事实】

| 事实 | 位置 |
|---|---|
| `Session` 结构体持有 `provider: StorageProvider` 引用 | `packages/document/document-service.ts:121-136` |
| 会话创建时一次性固定 `providerScope`（`providerId::canonicalRoot`）与 `resourceKey`（相对路径） | `document-service.ts:339-352`、`26-47` |
| 之后所有 IO 都走 `session.provider`，不再经过任何解析器 | `save:470`、`reload:571`、`reconcile:597`、`detectExternalChange:666` |
| `closeView` 只删视图，不动会话；`sessions`/`sessionsByResource` 从无删除路径 | `document-service.ts:369-393` |
| 复用会话时（非 dirty）会重新读盘以刷新基线 | `document-service.ts:288-334` |

结论：**会话是"Provider 对象的持有者"，不是"项目 ID 的引用者"**。任何"项目已失效"的判定都无法从会话自身推导，只能由外部注入。

### 1.2 服务端只有唯一 Provider【事实】

- `server.ts:230-233` 在启动时用 `options.rootDir` 建**一个** Provider。
- `server.ts:242` 的总线解析器是 `(providerId) => providerId === provider.providerId ? provider : undefined`，即只认 `'local'`。
- `/api/resources`（341）、`/api/document/disk`（356）都直接用这个模块级 `provider`。
- `/api/health` 返回 `{ status, mode, root: options.rootDir }`（336）。

### 1.3 根失效后的实际行为（运行时复现）

用真实模块在系统临时目录复现（脚本仅位于临时目录，未进入仓库）：

场景 A：**已存在文件**的会话，根被删除 / 被整体移动

```
--- root deleted
  save: CONFLICT ERR_DOCUMENT_VERSION_CONFLICT
  old root exists again: false
--- root moved
  save: CONFLICT ERR_DOCUMENT_VERSION_CONFLICT
  moved a.md: "# A\n"          （未写入，文件的旧内容保留）
```

场景 B：**尚未存在的文件**会话（`baseVersion === null`），根被删除 / 被整体移动

```
--- new-file session, root deleted
  save: COMMITTED
  old root recreated: true
  recreated file: "# new draft\n"
--- new-file session, root moved
  save: COMMITTED
  old root recreated: true
  recreated file: "# new draft\n"
```

根因链【事实】：

1. `writeConditional` 在版本比较通过后会 `mkdir(dirname, { recursive: true })`（`local-provider.ts:303`）。
2. `assertBoundaryStable` 用 `createRootBoundary(literalRoot)` 重建边界；根缺失时它走"锚定最近可解析祖先"分支（`path-safety.ts:141-170`），算出的 `canonicalRoot` 与原始值**字符串相同**，因此"边界稳定"检查通过。
3. `expectedVersion === null` 且 `currentVersion === null` 时版本比较通过（`local-provider.ts:281-288`）。

即：**"根被删除"在现有实现里不是可检测状态，而是一个可以被写操作"重建"的状态**。这直接违反 R1 的"不得静默写入其他目录/不得重建失效根"。

同时注意场景 A 的错误语义也是错的：项目不可用被报成 `ERR_DOCUMENT_VERSION_CONFLICT`，UI 会引导用户"用磁盘内容覆盖"，而磁盘上根本没有内容（`reload` 会再失败一次）。

### 1.4 目录身份可判别【已验证】

Windows NTFS 上 `stat().ino` 在"删除后重建同名目录"时**会变化**，`dev` 不变：

```
orig ino      28147497672359784  dev 1992047887
recreated ino 28428972649070440  dev 1992047887
```

因此 `dev:ino` 可以作为"根身份令牌"，把"根被替换成另一个同名目录"变成可检测事件（仅靠路径无法检测）。POSIX 同理。若某文件系统返回 `ino === 0`，按 fail-closed 处理（标记 `ROOT_IDENTITY_UNSUPPORTED`）。

### 1.5 授权维度现状【事实】

- `PermissionService` 已按 `providerId` 分维度，缺省 `'local'`，**不继承**（`permission-service.ts:115-117`、`146-152`）。
- 但服务端授予的是 `[{actorId, read, scope:''}, {actorId, write, scope:''}]`，**不带 providerId**（`server.ts:235-238`）。
- 多项目下若 `providerId = local:<projectId>`，这些全局 grant 一条都不命中 → 默认拒绝。这是**正确的失败方向**，但意味着必须改成"每项目一条授权"。

### 1.6 Shell 侧身份现状【事实】

| 事实 | 位置 |
|---|---|
| `DocTab` 没有 `projectId` 字段 | `apps/shell/src/state/types.ts:36-55` |
| `docId` 就是相对路径（`node.path ?? node.id`） | `DocumentActionsContext.tsx:176`、`ProjectTree.tsx:10` |
| 编辑队列按 `docId` 索引 | `DocumentActionsContext.tsx:119`、`133-168` |
| 保存锁按 `docId` 索引 | 同上 `124` |
| 草稿备份 key 只有路径：`ws:draft-backup:<path>` | `DocumentActionsContext.tsx:56-65` |
| 树展开状态按 `node.id`、选中按 `path` 存 | `types.ts:65-67`、`reducer` |

结论：**多项目下同名文件会在标签、队列、锁、草稿备份、展开状态五个位置全部串味**，且现有异步回填没有任何"响应归属"校验（`applyEdit` 回调只按 `docId` 找 tab，`DocumentActionsContext.tsx:154`）。

### 1.7 已核对但本轮不改的既有弱点【事实】

| 弱点 | 位置 | 本轮处置 |
|---|---|---|
| `/api/edit` 缺省 `expectedVersion` 时服务端自动用会话 `baseVersion` 补 | `server.ts:441-444` | 保留（不放大）；`applyEdit` 处理器本就不校验版本（`command-bus.ts:133-137`），该字段是装饰性的 |

## 2. 修订后的 Project Registry 接口【拟议】

### 2.1 数据来源

- 唯一来源：可信 JSON 配置文件，由启动参数给出（`--workspace <path>`），**只在进程启动时读取一次**。
- 不提供 HTTP 添加/删除/修改项目路径的接口（R5 硬约束）。
- 配置本身不接受请求体影响；配置里出现 UNC、相对路径、环境变量占位符 → 启动即拒绝。

```jsonc
{
  "version": 1,
  "projects": [
    { "projectId": "notes",  "name": "个人笔记", "rootDir": "D:/Work/notes" },
    { "projectId": "design", "name": "设计稿",   "rootDir": "D:/Work/design" }
  ]
}
```

### 2.2 接口（A1 必须实现）

```ts
export type ProjectStatus = 'READY' | 'UNAVAILABLE';

export type ProjectUnavailableReason =
  | 'MISSING'            // ENOENT
  | 'NOT_DIRECTORY'      // 存在但不是目录
  | 'PERMISSION_DENIED'  // EPERM/EACCES
  | 'REPARSE_POINT'      // 根本身是 junction/符号链接（身份可被改向）
  | 'CANONICAL_CHANGED'  // 运行期根身份令牌变化（被替换/重建）
  | 'UNC_UNSUPPORTED'    // A1 不支持网络路径
  | 'IO_ERROR';

/** 对外可交付（可安全序列化给浏览器）：不含 rootDir、不含 canonicalRoot。 */
export interface ProjectSummary {
  readonly projectId: string;
  readonly name: string;
  readonly status: ProjectStatus;
  readonly reason?: ProjectUnavailableReason;
}

export interface ProjectRegistry {
  /** 供 API 返回；顺序稳定（按配置顺序）。 */
  list(): readonly ProjectSummary[];

  /** Host 内部使用。 */
  get(projectId: string): ProjectHandle | undefined;

  /** 只有 READY 才返回 Provider；否则 undefined（调用方必须按 fail-closed 处理）。 */
  providerOf(projectId: string): StorageProvider | undefined;

  /**
   * 统一门禁（R1 核心）：
   * 1) projectId 必须存在于注册表；
   * 2) 状态必须 READY；
   * 3) 根身份令牌必须与 READY 时一致（防"删除后重建同名目录"）。
   * 任一不满足抛 ProjectGateError（带 errorCode），调用方不得降级。
   */
  assertUsable(projectId: string): ProjectHandle;

  /** 注册表结构版本；本项目启动后恒定（A1 无 refresh），留给 A2 的变更检测。 */
  version(): number;
}

export interface ProjectHandle {
  readonly projectId: string;
  readonly providerId: string;       // 'local:<projectId>'
  readonly rootDir: string;          // 仅 Host 内部
  readonly canonicalRoot: string;    // 仅 Host 内部
  readonly rootToken: string;        // `${dev}:${ino}`，仅 Host 内部
  readonly provider: StorageProvider;
}
```

| 能力 | 计划阶段 | 前置条件 |

## 3. 身份规则

### 3.1 逐项定义

| 标识 | Legacy（单项目） | Multi（多项目） | 生成方 |
|---|---|---|---|
| `projectId` | 不存在（内部常量 `legacy`，不出现在 API） | 配置声明，`^[a-z0-9][a-z0-9_-]{0,31}$` | 可信配置 |
| `providerId` | `local` | `local:<projectId>` | **Host 从 Registry 派生** |
| `resourceId` | `doc:<relativePath>` | `doc:<projectId>/<relativePath>` | **Host 派生**，客户端只能断言不能指定 |
| `providerScope`（内部） | `local::<canonicalRoot>` | `local:<projectId>::<canonicalRoot>` | DocumentService |
| `resourceKey`（内部） | `<relativePath>`（Windows 小写） | 同左（项目内唯一即可） | DocumentService |
| `sessionId` | `session-<n>` | 同左 | DocumentService，**不是凭证** |
| `actorId` | 服务端绑定 | 服务端绑定 | Gateway |

### 3.2 关键不变量

| 编号 | 不变量 | 现状 | 缺口 |
|---|---|---|---|
| ID-1 | 客户端不得指定 `providerId`/`resourceId`/`rootDir`/`actorId` | 已有 `rejectTrustedFields`（`server.ts:199-209`） | 需扩展为 multi 下**一律拒绝** `providerId`（旧代码放行 `'local'`） |
| ID-2 | `providerId` 必须由 Registry 按 `projectId` 解析 | 目前是 `claimedProviderId ?? 'local'`（`command-bus.ts:327`） | 需改为 `registry.providerIdOf(projectId)`，payload 里的 providerId 只用于一致性校验 |
| ID-3 | CommandBus 授权/审计必须用解析后的真实 Provider 身份 | 已满足（`target.providerId` 来自会话或解析结果） | 保留 |
| ID-4 | 同名文件跨项目不得共享 Session | 依赖 `resourceId` 已含 projectId | 需测试固化 |
| ID-5 | 同名文件跨项目不得共享授权 | 依赖 `providerId` 已含 projectId | 需每项目显式 grant |
| ID-6 | 同名文件跨项目不得共享草稿/队列/幂等结果 | Shell 侧尚无项目维度；幂等收据 key 为 `actorId::idempotencyKey` | **有缺口**：指纹已含 providerId（`command-bus.ts:439-446`），碰撞时会拒绝而非误用；但 Shell 侧必须按项目分键 |
| ID-7 | 同一运行实例禁止混用 Legacy/Multi | 无模式概念 | 需 `WS_WORKSPACE_MODE` 启动开关 |

### 3.3 「不能仅依赖刷新 Registry 的 Map」

`ERR_RESOURCE_IDENTITY_CONFLICT` 的现有机制（`document-service.ts:248-259`）只在 `openSession` 时生效，`applyEdit`/`save` 依靠 CommandBus 用 `identityFor()` 反查（`command-bus.ts:390-403`）。这条链路成立的前提是 `resolveProvider` 返回的**新** Provider 与旧会话的 `providerScope` 不同。

若 Registry 不重建 Provider（A1 就是这种情况），`resolveProvider` 仍返回旧对象，`providerScope` 必然相同 → **冲突检测形同虚设**。所以 R1 的门禁不能建立在"身份冲突"上，必须建立在**根活性 + 根身份令牌**上（§5.1）。

## 4. Legacy / Multi 兼容矩阵

### 4.1 模式开关

- `WS_WORKSPACE_MODE=legacy`（默认）：`node apps/server/src/main.ts <项目根>`，行为与 `08fc049` **完全一致**，`resourceId`/`providerId` 格式不变。
- `WS_WORKSPACE_MODE=multi`：`node apps/server/src/main.ts --workspace <config.json>`，新增 `projectId` 维度。
- 未显式设置时：给了 `--workspace` 即 multi，否则 legacy。二者互斥，启动即判定，运行期不可切换。

### 4.2 逐接口矩阵

### 4.3 唯一的破坏性变更：`/api/health` 移除 `root`

- 需求 §3.3 明确"服务端不得向浏览器返回 rootDir 等本机绝对路径"。
- 现状 `server.ts:336` 返回 `root`；`tests/suites/20-s9b-live-file.test.ts:127` **断言它必须等于真实根**。
- 处置建议：移除字段，改为不透明 `workspaceRef`（如 `ws-1`）。同步把该断言从"root 必须泄露"改为"响应中不得出现任何绝对路径分段"——这是**提高**断言强度，不是降低。
- **需要用户批准**：这修改了一条既有验收断言。

### 4.4 Legacy 兼容的验收底线

在 legacy 模式下，`tests/suites/20-s9b-live-file.test.ts`、`09-unauthorized`、`13-p0-1a`、`05/06/07/08` 中所有带 `providerId:'local'` 的 payload 必须**逐条通过**，除 §4.3 那一条。这是"增强安全不破坏旧客户端"的硬指标。

## 5. 根失效、重新绑定、旧 Session 与 dirty 草稿

### 5.1 统一门禁（R1 核心）【拟议】

在**每一次**触及项目的操作前执行，无例外、无降级：

```
CommandBus.dispatch
  → 解析目标（open: projectId+path / 其他: sessionId）
  → registry.assertUsable(projectId)          // R1-①②
  → 根身份令牌比对：handle.rootToken === 会话打开时的 rootToken   // R1-③④
  → 会话未标记 STALE                              // R1-⑤
  → 授权（providerId = handle.providerId）
  → 执行
```

直接读取入口（`/api/document/disk`、`/api/reload`、`/api/close`）必须调用**同一个** `assertUsable`，而不是复用 CommandBus 的结果缓存。

`assertUsable` 的四项判定（对齐 R3）：

| 步骤 | 判定 | 失败码 |
|---|---|---|
| 1 | `projectId` 在注册表中 | `ERR_PROJECT_NOT_FOUND` |
| 2 | 状态为 `READY` | `ERR_PROJECT_UNAVAILABLE`（携带 `reason`） |
| 3 | `statSync(rootDir)` 成功且 `isDirectory()` | `MISSING` / `NOT_DIRECTORY` |
| 4 | `realpathSync.native` 与 READY 时的 `canonicalRoot` 相同 | `CANONICAL_CHANGED` |
| 5 | `${dev}:${ino}` 与 READY 时的 `rootToken` 相同 | `CANONICAL_CHANGED`（"同名目录被替换"） |

成本：每次命令 1 次 `statSync` + 1 次 `realpathSync.native`。可在 A2 加短 TTL 缓存，A1 先不做（正确性优先）。

### 5.2 状态转换规则【拟议】

会话状态新增 `STALE`（不进入 `DocumentState` 的六态，而是**正交标记** `stale?: { reason, since }`，避免污染既有状态机与 `docs/06` 的断言）。

| 事件 | 会话 | 草稿 | 后续操作 | 错误码 |
|---|---|---|---|---|
| ① 根被删除/移动（R1-1） | 标记 STALE(reason=`ROOT_MISSING`) | **保留** | 读/编辑/保存/重载/重开全部拒绝 | `ERR_PROJECT_UNAVAILABLE` |
| ② Registry 标 UNAVAILABLE | 同 ① | 保留 | 同 ① | `ERR_PROJECT_UNAVAILABLE` |
| ③ Registry refresh 后 Provider 重建（**A2**） | 标记 STALE(reason=`REBOUND`) | 保留 | 同 ① | `ERR_SESSION_STALE` |
| ④ 旧会话仍绑定旧 Provider（R1-4） | 不迁移 | 保留 | 门禁令牌比对不通过即拒绝 | `ERR_SESSION_STALE` |
| ⑤ 用户重新打开同一 resourceId（R1-5） | 若存在 STALE 且 dirty → **拒绝**并回传草稿摘要 | 保留 | 需显式 `discardStaleDraft:true` 才允许新建会话 | `ERR_SESSION_STALE` |
| ⑥ 项目从注册表移除（R1-6） | 标记 STALE(reason=`PROJECT_REMOVED`) | 保留 | 同 ①；**磁盘文件不动** | `ERR_PROJECT_UNAVAILABLE` |

三条硬约束（全部为**拒绝**语义，而非"尽力而为"）：

1. **不丢弃 dirty 草稿**：STALE 会话的 `buffer` 仍可被 `getBuffer` 读出，供 UI 提示"复制草稿"；`closeView` 仍受 `ERR_DOCUMENT_DIRTY` 保护。
2. **不自动迁移**：不存在"把旧会话指向新 Provider"的代码路径；`openSession` 遇到 `providerScope` 不一致仍抛 `ERR_RESOURCE_IDENTITY_CONFLICT`（`document-service.ts:265-273`）。
3. **不静默写入其他目录**：门禁在 IO 之前，`writeConditional` 的 `mkdir` 不可能在失效根上执行（这正是 §1.3 场景 B 的修复点）。

### 5.3 重新打开流程（定义完整，实现分阶段）

```
open(projectId, path)
  ├─ 项目非 READY                          → ERR_PROJECT_UNAVAILABLE（含 reason）
  ├─ 存在同 resourceId 的 STALE 会话
  │    ├─ 非 dirty → 丢弃该会话，按新会话重新读盘（磁盘是唯一权威）
  │    └─ dirty    → 409 ERR_SESSION_STALE，响应携带
  │                   { staleDraftAvailable:true, staleReason, since, draftBytes }
  │                   （**不回传正文**，避免把草稿写进日志/浏览器历史；
  │                     正文仍可经 GET /api/document?sessionId= 读取）
  └─ 用户确认 → POST /api/open {projectId, path, discardStaleDraft:true}
       → 销毁 STALE 会话（草稿在 UI 侧已被用户复制）→ 新建会话
```

`discardStaleDraft` 与既有 `discardDraft`（`/api/reload`）保持同一语义约定：**服务端不替用户做丢弃决定**，缺省拒绝。

### 5.4 A1 的边界

- A1 实现：门禁 + `rootToken` + STALE 标记 + `discardStaleDraft` 流程的**拒绝分支**。
- A1 不实现：`refresh`、`rebind`、跨根 `adopt`。因此进程中 Provider 对象恒定，③④ 两条路径在 A1 **不可达**，但接口与状态机已定义，A2 落地时不需要改协议。
- 推论（需写进 README）：**A1 期间修改项目根路径必须重启进程**；重启后所有会话消失，不存在陈旧会话。
