## 1. 当前代码事实

### 1.1 会话与 Provider 的绑定方式【事实】

| 事实 | 位置 |
|---|---|
| `Session` 持有 `provider: StorageProvider` 引用 | `packages/document/document-service.ts:121-136` |
| 创建时一次性固定 `providerScope`（`providerId::canonicalRoot`）与 `resourceKey` | `document-service.ts:339-352`、`26-47` |
| 之后所有 IO 直接走 `session.provider`，无任何再解析 | `save:470`、`reload:571`、`reconcile:597`、`detectExternalChange:666` |
| `closeView` 只删视图；`sessions` / `sessionsByResource` 全无删除路径 | `document-service.ts:369-393` |
| 非 dirty 复用会话时会重新读盘刷新基线 | `document-service.ts:288-334` |

结论：**会话是"Provider 对象的持有者"，不是"项目身份的引用者"**。项目失效无法从会话自身推导，只能外部注入。

### 1.2 服务端只有唯一 Provider【事实】

- `server.ts:230-233` 启动时用 `options.rootDir` 建**一个** Provider。
- `server.ts:242` 的解析器只认 `provider.providerId`（即 `'local'`）。
- `/api/resources`（341）、`/api/document/disk`（356）直接用这个模块级 `provider`。
- `/api/health` 返回 `{ status, mode, root: options.rootDir }`（336）。

### 1.3 根失效后的实际行为（运行时复现）

用真实模块在系统临时目录复现（脚本只在临时目录，未进仓库）。**注意：复现完全不涉及 Registry，因此该缺陷在 Legacy Host 上同样成立（D-4）。**

场景 A：**已存在文件**的会话，根被删除 / 被整体移动

```
--- root deleted
  save: CONFLICT ERR_DOCUMENT_VERSION_CONFLICT
  old root exists again: false
--- root moved
  save: CONFLICT ERR_DOCUMENT_VERSION_CONFLICT
  moved a.md: "# A\n"          （新位置文件未被动过）
```

场景 B：**尚未存在的文件**会话（`baseVersion === null`），根被删除 / 被整体移动

```
--- new-file session, root deleted
  save: COMMITTED
  old root recreated: true
  recreated file: "# new draft\n"
--- new-file session, root moved
  save: COMMITTED
  old root recreated: true
  recreated file: "# new draft\n"
```

根因链【事实】：

1. `writeConditional` 在版本比较通过后执行 `mkdir(dirname, { recursive: true })`（`local-provider.ts:303`）。
2. `assertBoundaryStable` 用 `createRootBoundary(literalRoot)` 重建边界；根缺失时走"锚定最近可解析祖先"分支（`path-safety.ts:141-170`），算出的 `canonicalRoot` 与原始值**字符串相同**，于是"边界稳定"判定通过。
3. `expectedVersion === null && currentVersion === null` 时版本比较通过（`local-provider.ts:281-288`）。

即：**"根已消失"在现有实现中不是一个可检测状态，而是一个可以被写操作"重建"的状态**。场景 A 的错误语义同样是错的——项目不可用被报成版本冲突，UI 会引导用户做一次注定失败的"用磁盘覆盖草稿"。

### 1.4 `ino` 的精度事实【已验证】

`fs.statSync(path)`（number 模式）返回的 `ino` **已经丢失精度**：

```
number ino : 242631429925785950      Number.isSafeInteger = false
bigint ino : 242631429925785946
birthtimeNs: 1794544361234563600
roundtrip loses precision: true      // 相差 4，不是舍入而是错值
```

**因此 `dev:ino` 必须用 `fs.statSync(path, { bigint: true })` 读取，并以字符串形式（`${dev}:${ino}`）参与比较与存储**；任何经过 `Number`、`JSON.parse`（JSON 数字）或 `parseInt` 的环节都会把两个不同 inode 折叠成同一个令牌，使根替换检测静默失效。

重建后令牌变化【已验证，Windows NTFS】：

```
orig ino      28147497672359784  dev 1992047887
recreated ino 28428972649070440  dev 1992047887
```

即"删除后重建同名目录"可被令牌识别（仅靠路径无法识别）。

## 2. Project Registry 与根身份

### 2.1 数据来源【拟议】

唯一来源：可信 JSON 配置，由启动参数 `--workspace <path>` 给出，**进程启动时读取一次**，运行期不可变。无 HTTP 添加/删除/改路径接口。

```jsonc
{
  "version": 1,
  "projects": [
    { "projectId": "notes",  "name": "个人笔记", "rootDir": "D:/Work/notes" },
    { "projectId": "design", "name": "设计稿",   "rootDir": "D:/Work/design" }
  ]
}
```

配置层拒绝：相对路径、UNC、环境变量占位符、重复 `projectId`、`projectId` 不符合 `^[a-z0-9][a-z0-9_-]{0,31}$`。

### 2.2 接口（A1 必须实现）

```ts
export type ProjectStatus = 'READY' | 'UNAVAILABLE';

export type ProjectUnavailableReason =
  | 'MISSING'                  // ENOENT
  | 'NOT_DIRECTORY'            // 存在但不是目录
  | 'PERMISSION_DENIED'        // EPERM/EACCES
  | 'REPARSE_POINT'            // 根本身是 junction/符号链接
  | 'CANONICAL_CHANGED'        // 运行期规范根变化
  | 'ROOT_TOKEN_CHANGED'       // 同名目录被替换（dev:ino 变化）
  | 'ROOT_IDENTITY_UNSUPPORTED'// ino 不可用（见 §2.3）
  | 'UNC_UNSUPPORTED'
  | 'IO_ERROR';

/** 可安全序列化给浏览器：不含 rootDir / canonicalRoot / rootToken。 */
export interface ProjectSummary {
  readonly projectId: string;
  readonly name: string;
  readonly status: ProjectStatus;
  readonly reason?: ProjectUnavailableReason;
}

export interface ProjectRegistry {
  list(): readonly ProjectSummary[];
  get(projectId: string): ProjectHandle | undefined;
  providerOf(projectId: string): StorageProvider | undefined;
  /** 统一门禁：不存在/非 READY/根身份变化 → 抛 ProjectGateError。 */
  assertUsable(projectId: string): ProjectHandle;
  /** A1 恒为 1；预留给 A2 的变更检测。 */
  version(): number;
}

export interface ProjectHandle {
  readonly projectId: string;
  readonly providerId: string;    // 'local:<projectId>'
  readonly rootDir: string;       // 仅 Host 内部
  readonly canonicalRoot: string; // 仅 Host 内部
  /** `${dev}:${ino}:${birthtimeNs}`，全部来自 bigint stat，字符串形式。 */
  readonly rootToken: string;
  readonly provider: StorageProvider;
}
```

### 2.3 `rootToken` 的读取、复用风险与支持条件

**读取规范（强制）**

```ts
const s = fs.statSync(real, { bigint: true });   // 绝不用 number 模式
const token = `${s.dev}:${s.ino}:${s.birthtimeNs}`;
```

- `dev` / `ino` / `birthtimeNs` 全部为 `BigInt`，只做字符串拼接，**不参与任何算术语义比较**。
- 令牌**不得**作为 JSON 数字出网；对外只允许出现在不透明的 `workspaceRef` 中（或干脆不出现）。
- 任何日志/审计记录令牌时必须是字符串，禁止先转 `Number`。

**为什么必须 BigInt**【已验证】：见 §1.4，number 模式实测偏差为 4，且 `Number.isSafeInteger` 为 false。用 number 会导致"不同 inode 得到同一令牌"，根替换检测失效且无任何报错。

**inode 复用风险（残余，不可完全消除）**

- NTFS/ext4 在文件删除后会**复用** file id / inode；仅凭 `ino` 无法区分"同一个目录"与"新建但复用了同一 id 的目录"。
- 因此令牌加入 `birthtimeNs`：重建目录的创建时间必然不同，实测可区分。
- **仍不能排除**的极端情形：卷级回滚/快照恢复导致 `dev+ino+birthtimeNs` 全部复现。此时令牌比对会通过。
- 补偿控制（不依赖令牌的部分）：
  1. **会话级令牌**：会话打开时记录当时的 `rootToken`，每次写前同时比对"当前令牌 == 会话令牌"（§5.4 C1）。根被替换且 Registry 尚未感知时，会话令牌仍能拦住。
  2. **写入层连续性检查**在 IO 前失败即返回 `ERR_ROOT_CHANGED`，绝不进入 `mkdir`/`rename`。
  3. **草稿永不自动落盘**：任何令牌可疑都走"拒绝 + 保留草稿"路径，不做"尽力写入"。
- 结论：令牌是**检测手段**，不是安全证明；真正的安全保证来自"失败即拒绝 + 不自动迁移"。

**文件系统支持条件（fail-closed）**

| 情形 | 处置 |
|---|---|
| `statSync(..., {bigint:true})` 抛错（EPERM/EACCES/EIO） | 拒绝注册，`IO_ERROR` / `PERMISSION_DENIED` |
| `ino === 0n`（部分 FAT/exFAT、部分网络 FS 的合成值） | 拒绝注册，`ROOT_IDENTITY_UNSUPPORTED` |
| `birthtimeNs === 0n` | 允许，但令牌退化为 `dev:ino`，并在 `ProjectSummary` 上不外露的情况下记入诊断日志 |
| UNC / 网络盘 / 映射盘 | A1 直接拒绝 `UNC_UNSUPPORTED`（不做可达性探测，避免挂起） |
| 大小写不敏感卷 | 规范根比较沿用 `samePath`（Windows 小写化），令牌比较**大小写无关不适用**（令牌是数字串） |

**【假设 A-1】** 目标用户全部盘符（含 exFAT 移动盘）行为一致——**未验证**，需在 A1 前补一条真机探测；若 exFAT 返回 `ino === 0n`，该盘上的项目将被拒绝注册（可接受的失败方向），但必须在 README 明确写清。

### 2.4 仅作未来扩展（A1 不实现、不暴露）

| 能力 | 阶段 | 前置条件 |

## 3. 身份规则

### 3.1 逐项定义

| 标识 | Legacy | Multi | 生成方 |
|---|---|---|---|
| `projectId` | 不存在（内部常量 `legacy`，不出现在 API） | 配置声明 | 可信配置 |
| `providerId` | `local` | `local:<projectId>` | **Host 从 Registry 派生** |
| `resourceId` | `doc:<relativePath>` | `doc:<projectId>/<relativePath>` | **Host 派生**，客户端只能断言 |
| `providerScope`（内部） | `local::<canonicalRoot>` | `local:<projectId>::<canonicalRoot>` | DocumentService |
| `resourceKey`（内部） | `<relativePath>`（Windows 小写） | 同左 | DocumentService |
| `rootToken`（内部） | 打开时捕获 | 同左 | Storage / DocumentService |
| `sessionId` | `session-<n>` | 同左 | DocumentService，**不是凭证** |

### 3.2 不变量

| 编号 | 不变量 | 现状 | 缺口 |
|---|---|---|---|
| ID-1 | 客户端不得指定 `providerId`/`resourceId`/`rootDir`/`actorId` | `rejectTrustedFields`（`server.ts:199-209`） | multi 下必须**一律拒绝** `providerId`（现放行 `'local'`） |
| ID-2 | `providerId` 由 Registry 按 `projectId` 解析 | 现为 `claimedProviderId ?? 'local'`（`command-bus.ts:327`） | 删除该回退；payload 的 `providerId` 只用于一致性校验 |
| ID-3 | 授权/审计使用解析后的真实 Provider 身份 | 已满足 | 保留 |
| ID-4 | 同名文件跨项目不共享 Session | 依赖 `resourceId` 含 projectId | 需测试固化 |
| ID-5 | 同名文件跨项目不共享授权 | 依赖 `providerId` 含 projectId | 需每项目显式 grant |
| ID-6 | 不共享草稿/队列/锁/幂等结果 | 指纹已含 providerId（`command-bus.ts:439-446`） | Shell 侧必须补项目维度 |
| ID-7 | 同进程禁止混用 Legacy/Multi | 无模式概念 | 启动开关 `WS_WORKSPACE_MODE` |

### 3.3 身份来源规则（本轮新增，对应修订 ③）

| 请求类别 | 端点 | 身份来源 |
|---|---|---|
| **项目作用域**（无会话） | `GET /api/resources`、`POST /api/open` | **必须带 `projectId`**；`providerId` 由 Registry 反查，客户端不得提供 |
| **会话作用域**（已绑定） | `GET /api/document`、`GET /api/document/disk`、`POST /api/edit`、`POST /api/save`、`POST /api/reload`、`POST /api/close` | **只用 `sessionId`**，项目与 Provider 均由服务端从会话身份解析。若请求里出现 `projectId`：一致则忽略（不作为来源），不一致 → `400 ERR_COMMAND_INVALID` |
| 项目枚举 | `GET /api/projects` | 无参数 |

理由【拟议】：会话已经固化了 `providerScope` 与 `rootToken`，让客户端重新声明项目等于允许"用 A 的声明去操作 B 的会话"这一类混淆；把项目维度完全收进服务端身份，是多项目下唯一不会随客户端状态漂移的设计。

### 3.4 "不能仅依赖刷新 Registry 的 Map"

`ERR_RESOURCE_IDENTITY_CONFLICT`（`document-service.ts:248-259`）只在 `openSession` 生效；`applyEdit`/`save` 依赖 CommandBus 用 `identityFor()` 反查（`command-bus.ts:390-403`），前提是 `resolveProvider` 返回的 Provider 与旧会话 `providerScope` **不同**。

A1 不重建 Provider，`resolveProvider` 恒返回同一对象，`providerScope` 必然相同 → **该冲突检测形同虚设**。因此 R1 门禁不能建立在"身份冲突"上，必须建立在**根活性 + 根身份令牌 + 写入层连续性**三者之上（§5.1、§5.4）。

## 4. Legacy / Multi 兼容矩阵

### 4.1 模式开关

- `WS_WORKSPACE_MODE=legacy`（默认）：`node apps/server/src/main.ts <项目根>`，行为与 `08fc049` 一致。
- `WS_WORKSPACE_MODE=multi`：`node apps/server/src/main.ts --workspace <config.json>`。
- 未显式设置时：给 `--workspace` 即 multi，否则 legacy。启动即定，运行期不可切换。

### 4.2 逐接口矩阵

| 接口 | Legacy 请求 | Legacy 响应 | Multi 请求 | Multi 响应 | 兼容性 |
|---|---|---|---|---|---|
| `GET /api/health` | 无变化 | `{status, mode}`，**移除 `root`** | 同 | 同 + `workspaceMode` | ⚠ 见 §4.3 |

### 4.3 Health 隐私：可改与不可改的断言边界

**新契约**：`/api/health` 不返回任何本机绝对路径（`rootDir`、`canonicalRoot`、盘符、UNC 均不得出现）。本机绝对路径只允许出现在 Host 的控制台输出与本地日志中，不得进入任何 HTTP 响应。

**唯一允许的断言更新**（且必须**加强**）：
`tests/suites/20-s9b-live-file.test.ts:127`

```diff
- assert.equal(health.body.root, root);          // 断言必须泄露绝对路径
+ assert.equal('root' in health.body, false);                    // 不得再返回 root
+ assert.doesNotMatch(JSON.stringify(health.body), /[A-Za-z]:[\\/]|\\\\|\/Users\/|\/home\//);
```

理由：原断言把"泄露本机根"写成了验收条件，与新安全契约直接冲突；修改后不再是"放宽"，而是**从"必须泄露"改成"必须不泄露"**，覆盖面更大（含其它字段误带路径的情形）。该条变更需用户批准（ADR-019）。

1. `S9B-01`：只绑定回环、关闭后拒绝连接。
2. `S9B-02`：拒绝客户端 `rootDir`、`../` 越界、绝对路径；根外文件字节不变、目录项不变。

## 5. 根失效、旧 Session 与草稿

### 5.1 双门禁模型（R1 核心，修订后）

| 门禁 | 保护对象 | 触发点 | 判定 | 失败码 |
|---|---|---|---|---|
| **G-DISK（磁盘门禁）** | 磁盘读写 | 所有触及文件的命令与直接读盘接口 | 注册存在 → READY → 目录存在 → `canonicalRoot` 一致 → `rootToken` 一致 → 会话令牌一致 | `ERR_PROJECT_UNAVAILABLE` / `ERR_SESSION_STALE` |
| **G-DRAFT（草稿门禁）** | 内存中的会话缓冲 | `GET /api/document` 返回正文、`getBuffer` | **actor == 会话创建者** ∧ `sessionId` 存在 ∧ `viewId` 属于该会话 | `ERR_PERMISSION_DENIED` / `ERR_DOCUMENT_NOT_FOUND` |

**分界原则**：项目失效**只**封锁磁盘（G-DISK），**不**封锁"用户取回自己尚未保存的文字"（G-DRAFT）。反过来，G-DRAFT 通过**绝不**意味着可以写盘——写盘永远要再过 G-DISK。

`assertUsable` 的五步判定（G-DISK 的公共实现）：

| 步骤 | 判定 | 失败 reason |
|---|---|---|
| 1 | `projectId` 在注册表 | `ERR_PROJECT_NOT_FOUND` |
| 2 | 状态 READY | 原 `reason` |
| 3 | `statSync(rootDir)` 成功且 `isDirectory()` | `MISSING` / `NOT_DIRECTORY` |
| 4 | `realpathSync.native` == READY 时 `canonicalRoot` | `CANONICAL_CHANGED` |
| 5 | bigint 令牌 == READY 时 `rootToken` | `ROOT_TOKEN_CHANGED` |

成本：每命令 1 次 `realpath` + 2 次 `stat`（其中一次 bigint）。**【A2】** 可加短 TTL 缓存；A1 不做（正确性优先）。

### 5.2 会话状态：STALE 作为正交标记

`STALE` **不进入** `DocumentState` 六态（避免污染 `docs/06` 状态机与既有断言），而是会话上的正交字段：

```ts
interface SessionStale { reason: ProjectUnavailableReason | 'REBOUND' | 'PROJECT_REMOVED'; since: string; }
```

状态转换：

| 事件 | 会话 | 草稿 | 磁盘操作 | 草稿读取 | 归属 |
|---|---|---|---|---|---|
| ① 根被删除/移动 | STALE(`MISSING`) | 保留 | 拒绝 | **允许**（G-DRAFT） | A1 |
| ② Registry 标 UNAVAILABLE | STALE | 保留 | 拒绝 | 允许 | A1 |
| ③ 同名目录被替换 | STALE(`ROOT_TOKEN_CHANGED`) | 保留 | 拒绝 | 允许 | A1 |
| ④ Provider 被重建 | STALE(`REBOUND`) | 保留 | 拒绝 | 允许 | **A2** |
| ⑤ 项目从注册表移除 | STALE(`PROJECT_REMOVED`) | 保留 | 拒绝 | 允许 | **A2** |
| ⑥ 会话被回收（无视图、非 dirty、非 STALE） | 正常回收 | 无 | — | — | **A2** |

### 5.3 重新打开流程【A1 实现"拒绝分支"，A2 实现"恢复分支"】

```
open(projectId, path)
  ├─ G-DISK 不通过                     → ERR_PROJECT_UNAVAILABLE(reason)
  ├─ 存在同 resourceId 的 STALE 会话
  │    ├─ 非 dirty ────────────────────→ 丢弃该会话，新建会话重新读盘（磁盘为唯一权威）
  │    └─ dirty  ──→ 409 ERR_SESSION_STALE
  │                    { staleReason, since, draftBytes, draftRecoverable:true }
  │                    （**不回传正文**，正文走 G-DRAFT 的既有接口按 view 读取）
  └─ 用户确认 → POST /api/open {projectId, path, discardStaleDraft:true}
       → 作废 STALE 会话（草稿须已被用户取走）→ 新建会话
```

- `discardStaleDraft` 与既有 `discardDraft`（`/api/reload`）同语义：**服务端不替用户做丢弃决定**，缺省拒绝。
- **不自动迁移**：不存在"把旧会话指向新 Provider"的代码路径；`providerScope` 不一致时仍抛 `ERR_RESOURCE_IDENTITY_CONFLICT`（`document-service.ts:265-273`）。
- **A1 不实现**"根恢复后自动复活 STALE 会话"：A1 无 `refresh`，令牌变化后无法自愈，只能重启（§5.7）。

### 5.4 写入层强制检查点（修订 ①，本轮新增核心）

规则：**根身份校验不得只存在于 CommandBus**。Registry/CommandBus 只是"第一道门"；StorageProvider 作为唯一写入原语，必须在每个可能产生副作用/目录的节点独立复核，且失败必须返回 `FAILED`（绝不 `COMMITTED`/`UNKNOWN`）。

`RootBoundary` 扩展为携带连续性凭据：

```ts
interface RootBoundary {
  literalRoot: string; canonicalRoot: string; verified: boolean; anchor: string;
  rootToken: string | null;   // 构造时若根已存在则捕获（bigint 令牌）
}
```

`writeConditional` 的检查点序列：

| 检查点 | 时机 | 检查内容 | 违反时 |
|---|---|---|---|
| **C0** | 解析路径后、读版本前 | `assertRootContinuity(boundary)`：若 `boundary.verified === true`，要求根仍存在且令牌一致；若 `verified === false`（构造时根不存在），允许继续但记录 `pendingCreation` | `FAILED` / `ERR_ROOT_CHANGED` |
| **C1** | `mkdir` **之前** | 同 C0 **再校验一次**（防止 C0 与 mkdir 之间的窗口）；本次会话令牌 == 当前令牌（由 DocumentService 传入期望令牌） | `FAILED` / `ERR_ROOT_CHANGED`，**不得 mkdir** |
| **C2** | `mkdir` **之后**、写临时文件前 | 重新 `resolveInBoundary`（已有） + `assertBoundaryStable`（已有） + 令牌复核 + **`dirname(tempPath)` 必须位于 `canonicalRoot` 之内**（`isInsideRoot` 复核，防止临时文件落在替换后的根） | `FAILED`，清理临时文件 |
| **C3** | `rename` **之前** | 再复核令牌（已有 `assertBoundaryStable` 保留） | `FAILED`，清理临时文件 |
| **C4** | `rename` **之后** | 写后复核：目标文件确在 `canonicalRoot` 内且令牌未变 | **`UNKNOWN`**（副作用可能已发生，不得报 COMMITTED） |

补充规定：

- `verified === false` 的边界（"根尚不存在"）**只允许第一次写入创建根**；根被创建后立刻升级边界（`verified = true`，捕获 `rootToken`），后续写入按 C1–C4 严格执行。这正是 **S4R-05**（`15-s4r-root-identity.test.ts:196`，断言"根不存在时初始化允许创建、后续写入照常"）仍然成立的原因——**不改该测试，不改 `createRootBoundary` 语义**。
- `read` / `stat` / `list` 在连续性失败时必须抛 `ERR_ROOT_CHANGED`（而不是伪装 `ERR_RESOURCE_NOT_FOUND`），使 D-1 的"误报版本冲突"变成"项目不可用"。
- `ERR_ROOT_CHANGED` 是新存储层错误码，服务端映射为 `ERR_PROJECT_UNAVAILABLE`（HTTP 503），并与 `ERR_PATH_OUTSIDE_ROOT`（403）区分：前者是"运行期根消失/被替换"，后者是"请求路径越界"。

### 5.5 草稿恢复门禁（修订 ④）

| 维度 | 磁盘访问（G-DISK） | 草稿恢复（G-DRAFT） |
|---|---|---|
| 对象 | 文件系统 | 内存缓冲（`session.buffer`） |
| 依据 | 项目注册状态 + 根身份令牌 | actor + session + view 三重绑定 |
| 项目失效时 | **拒绝** | **允许**（用户必须能拿回自己的文字） |
| 项目被移除 | 拒绝 | 允许（会话仍在内存） |
| 校验实现 | `registry.assertUsable` + 会话令牌 | `views.get(viewId).sessionId === sessionId` ∧ `view.actorId === ctx.actorId` ∧ 会话存在 |
| 失败码 | `ERR_PROJECT_UNAVAILABLE` | `ERR_PERMISSION_DENIED` / `ERR_DOCUMENT_NOT_FOUND` |

细化要求：

1. `ViewRecord` 必须**记录创建该视图的 actorId**（现结构只有 `sessionId/resourceId/path`，`server.ts:211-215`）；`requireView` 改为同时校验 actor。**跨 actor 凭 `sessionId` 猜读草稿必须失败。**
2. `GET /api/document` 在 STALE 状态下**只返回** `{ sessionId, resourceId, path, content, baseVersion, revision, dirty, documentState, stale:{reason,since} }`，不再执行 `authorizeRead`（那是对磁盘资源的授权）；但**必须**执行 G-DRAFT。
3. `GET /api/document/disk` 是**磁盘**接口：STALE 时一律 503，不返回任何内容（连"磁盘上没有"都不透露）。
4. 草稿**不写入**任何磁盘文件（含临时文件）；`discardStaleDraft` 是唯一的销毁入口，且需要显式确认。
5. 草稿正文**不进日志**（沿用既有日志策略）：只允许记录 `draftBytes`。

### 5.6 Legacy Host 的同一缺陷与修复边界（修订 ①）

- 【事实】§1.3 的复现**没有**任何 Registry 参与，`server.ts` 的单 Provider 也一样中招。所以 D-1 **不是多项目引入的问题**，是既有 Storage/Document 的实现缺陷。

- **不破坏既有 Storage 测试的边界**（逐条核对）：

| 既有用例 | 约束 | 是否受本次修复影响 |
|---|---|---|
| `S4R-05`（`15:196`）根不存在时初始化 | 首次写入**必须**能创建根 | 不受影响：`verified:false` 分支显式允许首次创建 |

| `16-s4r-stat-semantics` | `exists` 与 `contentVersion` 不得自相矛盾 | 不受影响：只改错误映射（`ERR_ROOT_CHANGED` 只在根消失时出现） |

- **不改**任何现有测试；新增用例只加在 `23/24` 套件（§7）。若某个既有用例意外失败，视为修复越界，必须回退设计而不是改断言。

### 5.7 A1 的边界（修订 ⑤）

- **A1 实现**：G-DISK / G-DRAFT 双门禁、`rootToken`、C0–C4、STALE 标记、`discardStaleDraft` 的**拒绝分支**、项目列表与状态展示。

## 8. ADR 候选（最终）

正式编号接续 `docs/16`（现有至 ADR-013）：ADR-1→ADR-014 … ADR-7→ADR-020。

| ADR | 标题 | 决策要点 | 阶段 | 需批准 |
|---|---|---|---|---|
| ADR-014（ADR-1） | 多项目采用 `local:<projectId>` 命名空间，Legacy/Multi 双轨互斥 | 禁止同进程混用；legacy 格式冻结 | A1 | 是 |
| ADR-015（ADR-2） | Registry 是唯一可信项目来源，仅本地 JSON，无 HTTP 变更 | 项目根只能来自启动配置 | A1 | 是 |
| ADR-016（ADR-3） | 根身份 = 路径规范 + 存在 + 可访问 + **bigint `dev:ino:birthtimeNs` 令牌**；写入层 C0–C4 独立复核 | 令牌仅检测手段；失败一律拒绝；`ino===0n` fail-closed；`verified:false` 仅允许创建一次根 | A1 | 是（令牌字段与 FS 支持范围） |
| ADR-017（ADR-4） | 磁盘门禁与草稿门禁分离；STALE 正交标记；不迁移、不自动丢弃 | 草稿恢复需 actor+session+view 三重绑定 | A1 | 是 |
